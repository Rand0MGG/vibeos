# VibeOS 产品章程

状态：已确认产品方向
更新日期：2026-07-15

## 1. 项目使命

VibeOS 要构建一个以 Agent 为核心的个人计算层。用户负责表达目标、边界和
现实世界承诺，Agent 负责理解整台电脑、选择最有效的操作方式、持续执行
任务、处理故障，并判断目标是否完成。

一句话定义：

> VibeOS 是运行在个人 Linux 设备上的 Agent-native 计算运行时：它通过
> API、命令行、系统服务和图形界面使用电脑，并通过权限、秘密、事务、
> 回滚和审计机制对这种能力进行治理。

“像真实用户一样使用电脑”是最低能力要求，不是能力上限。Agent 应当能
使用人类可见的界面，也应发挥它直接调用 API、分析日志、管理进程和理解
系统状态的优势，比普通用户更全面地了解这台机器。

## 2. 产品判断

传统桌面助手通常把 Agent 限制成少量命令或应用意图的调用器；通用
computer-use 系统又经常只模仿点击和输入，没有利用操作系统提供的结构化
能力。两种路线都没有充分发挥 Agent 的优势。

VibeOS 的核心判断是：

1. Agent 应持有一个持续更新的机器模型，而不是每次只看一句请求；
2. API、CLI 和系统服务是主要执行面，鼠标键盘是通用兜底能力；
3. 用户给出明确任务后，Agent 应自主处理技术细节，而不是逐步请求许可；
4. 目标含义不清时必须先澄清，不能擅自替用户选择真实意图；
5. 产生外部承诺、不可逆破坏或重大安全变化时必须由用户批准；
6. 系统级变更必须尽可能事务化，并在执行前准备真实可用的回滚路径；
7. Agent 可以主动发现和报告问题，但是否创建修复任务由用户决定；
8. 高质量推理主要使用云端模型，本地模型和确定性策略负责隐私、路由和
   低成本处理；
9. 先在现有 Linux 发行版上证明 Runtime，保留未来演进为 Agent-native
   Linux 发行版的能力。

## 3. 要解决的问题

个人电脑拥有大量相互割裂的接口、应用、配置和状态。用户既不了解所有底
层信息，也不应该亲自处理每个机械步骤。现有自动化主要存在以下问题：

- 用户需要描述具体步骤，而不是只表达目标；
- 脚本只覆盖预先知道的路径，环境变化后容易失效；
- UI Agent 只会模仿人类操作，没有利用 API、日志和命令行；
- 系统级 Agent 获得过大权限后缺少独立审核、秘密隔离和回滚；
- 长时间任务无法可靠等待、恢复和处理中途变化；
- 云端模型能力强，但把整台机器的内容直接发送到云端不可接受；
- Agent 往往把动作成功误判成用户目标完成。

VibeOS 要把这些问题统一为一个产品：用户交付目标，Agent 获得对机器的
受治理操作能力，并对执行过程和最终结果负责。

## 4. 目标用户

### 首要用户

- 希望把重复或复杂电脑任务交给 Agent 的 Linux 个人用户；
- 愿意让 Agent 深入理解本机状态，但要求关键行为可控、可回滚、可追溯的
  技术用户；
- 需要持续数小时执行开发、研究、系统维护或信息处理任务的用户。

### 次要用户

- 为 Agent 增加系统、开发、办公或应用能力的开发者；
- 研究 Agent 权限、长期任务、模型路由和人机协作的工程团队；
- 希望把专用应用能力接入本地个人 Agent 的应用作者。

### 当前范围

首个受支持环境是 GNOME Wayland Linux。Windows、macOS 和其他桌面环境
不是近期交付目标，但核心任务、权限和模型路由概念不应被 GNOME 特有实现
锁死。

## 5. 用户与 Agent 的职责

### 用户负责

- 表达真实目标、范围和偏好；
- 在目标有歧义时补充意图；
- 批准现实世界承诺、不可逆破坏和重大安全变化；
- 决定是否处理 Agent 主动发现的问题；
- 设置长期授权、隐私策略和模型使用偏好；
- 必要时接管、暂停、取消或修改任务。

### Agent 负责

- 建立并维护对机器、应用和任务环境的理解；
- 判断任务是否足够明确，不明确时先提问；
- 分解目标、选择工具和调整计划；
- 优先使用可靠的 API、CLI 和系统服务；
- 必要时使用 Accessibility、鼠标、键盘和视觉；
- 主动处理技术错误、等待外部状态并恢复中断任务；
- 为特权变更提出风险、验证和回滚方案；
- 收集证据并自行判断目标是否完成；
- 报告无法完成的原因和可行下一步。

## 6. 核心产品模型

### 6.1 任务契约

自然语言请求不能直接等同于可执行任务。系统先形成任务契约，至少包含：

- 用户目标；
- 已知范围和约束；
- 完成条件；
- 允许产生的副作用；
- 必须再次询问用户的决策点；
- 时间、成本和资源限制。

目标或后果存在实质歧义时，Agent 必须在执行前询问用户。任务契约明确
后，Agent 可以自主处理契约范围内的技术步骤。

### 6.2 机器模型

Machine Model 是 VibeOS 的核心资产。它应持续理解：

- 硬件、操作系统、内核和驱动；
- 软件包、应用、版本和依赖；
- 进程、服务、作业和日志；
- 文件、配置、存储和备份状态；
- 网络、设备和会话；
- 用户账号、权限和可用能力；
- 当前桌面、窗口和应用状态；
- 历史故障、变更、任务和验证结果。

机器模型不是把所有原始内容永久复制进数据库，而是受隐私和保留策略治理
的结构化索引、状态快照、证据引用和时间线。

### 6.3 持久化任务运行时

任务必须可以持续数小时、等待、暂停、恢复和在机器重启后继续。运行时应
持久化 Goal、Task、Plan、Attempt、Action、Observation、Decision 和
Evidence，而不是依赖一次模型对话保持状态。

### 6.4 统一动作层

Agent 根据可靠性、成本和可验证性选择执行面：

```text
系统或应用 API
  -> 命令行和系统工具
  -> D-Bus / Portal / 系统服务
  -> Accessibility
  -> 结构化 UI 自动化
  -> 鼠标、键盘、截图、OCR 和视觉定位
```

Shell 是一等执行能力，但不能等同于不受治理的 root shell。命令必须进入
统一的影响判断、权限、审计、验证和回滚流程。

## 7. 权限和现实世界影响

VibeOS 不采用“每一步都询问”的模式，也不允许主 Agent 自行无限提权。

### 可以自主执行

- 观察和读取任务所需的本机状态；
- 在任务契约和既有权限内执行可逆本地操作；
- 运行普通命令、调用 API 和操作应用；
- 处理中间失败、等待和不扩大影响范围的替代方案；
- 主动分析问题并向用户提出建议。

### 必须由用户批准

- 付款、购买、预订或其他财务承诺；
- 发送邮件、消息、公开发布或代表用户表达立场；
- 上传、共享或公开私人数据；
- 删除重要数据或执行难以恢复的大范围破坏；
- 卸载关键软件或修改账号、权限、网络与安全策略；
- 创建账号、接受协议或形成法律和现实世界承诺；
- 缺少可信回滚路径的高风险系统变更。

用户可以通过明确的长期授权策略减少可逆本地操作的重复确认，但授权必须有
范围、期限、资源和撤销方式。当前产品基线中，长期授权不能替代 E3 行为的
逐次用户批准：付款、外部通信、私人数据外传、不可逆破坏和重大账号或安全
变化仍需在执行前交给用户决定。

## 8. 提权、事务和回滚

主 Agent 应在普通权限和受控 Sandbox 中运行。需要系统权限时，它提交一
个结构化提权请求，而不是直接获得长期 root 凭据。

提权请求至少描述：

- 与哪个任务契约绑定；
- 需要执行的准确操作；
- 目标资源和权限范围；
- 预期效果和风险；
- 回滚计划；
- 执行后健康检查；
- 权限有效期和使用次数。

静态策略和独立 Reviewer Agent 共同审核请求，Privilege Broker 使用临时
权限执行获批操作。这里的 Reviewer 仍是 VibeOS 自动运行的 Agent 角色；
“独立”表示它与执行主 Agent 隔离，而不是要求用户逐次审核所有可回滚提权。
执行主 Agent 不能成为自己的唯一审批者。

每项动作需要被分类为：

- **可回滚**：能够恢复到明确的执行前状态；
- **可补偿**：不能原样撤销，但存在受控的反向动作；
- **不可逆**：无法可靠撤销，必须依赖用户事前批准。

系统级变更应遵循：

```text
捕获前置状态
  -> 创建备份、快照或逆操作
  -> 执行限定变更
  -> 观察和健康检查
  -> 成功提交
  -> 失败自动回滚
  -> 验证回滚结果
```

系统不能虚假承诺所有动作都能回滚。付款、消息发送、数据泄露等不可逆行
为必须在执行前由用户决策。

## 9. Secret Broker

密码、Token、Cookie、私钥和恢复码不应进入 Agent 或模型上下文。Agent
只使用类似 `secret://service/account` 的引用。

Secret Broker 负责：

- 验证任务、目标程序、域名、账号和授权范围；
- 将秘密直接注入受信程序或协议；
- 限制使用次数和有效时间；
- 防止通过日志、参数、环境、剪贴板和截图回读；
- 记录“哪个任务使用了哪个秘密引用”，但不记录明文。

## 10. 云端与本地模型

VibeOS 默认允许使用 GPT、DeepSeek 等云端模型完成高质量理解、规划和判断，
同时通过 Context and Model Router 控制发送内容。

路由顺序是：

```text
确定性隐私策略
  -> 数据敏感级别判断
  -> 上下文裁剪和结构化
  -> 脱敏或本地摘要
  -> 能力、成本和延迟判断
  -> 云端或本地模型
```

基础数据等级：

- **公开数据**：允许发送云端；
- **普通机器元数据**：按任务需要结构化后发送；
- **私人内容**：仅在任务必要且用户策略允许时发送，并最小化上下文；
- **秘密材料**：永远不发送给本地或云端模型，只能交给 Secret Broker；
- **用户指定本地数据**：不得越过用户设置的本地处理边界。

模型不能自己决定绕过硬隐私策略。确定性规则负责硬边界，本地模型可以帮
助分类和摘要，云端模型负责需要高能力的推理。

## 11. 主动行为

Agent 可以主动监控和发现：

- 磁盘、资源和系统健康问题；
- 服务异常、失败任务和配置漂移；
- 可用更新、已知风险和维护机会；
- 用户长期任务中的阻塞或新信息。

默认行为是收集证据、解释影响并提出建议。是否创建解决任务由用户决定。
只有用户预先建立明确的长期授权策略后，Agent 才能自动处理对应的 E0/E1
问题；E2 仍需独立 Reviewer，E3 仍需逐次用户批准。

## 12. 产品形态和发行版路径

### 近期产品

VibeOS 首先作为可安装在现有 Linux 发行版上的 Runtime 交付。这样可以先
验证 Agent、机器模型、长期任务、提权、秘密、模型路由和真实用户价值。

### 长期可能形态

如果 Runtime 证明现有发行版无法可靠提供以下能力，可以启动 Agent-native
Linux 发行版：

- 事务式系统变更和可启动回滚；
- 统一权限、秘密和 Agent 生命周期；
- 原子系统更新和版本化机器状态；
- Agent 优先的人机交互、恢复和安全策略；
- Runtime、桌面和系统服务的一致发布。

发行版是验证结果驱动的战略选择，不是当前阶段的先决条件。

## 13. 产品原则

1. **用户目标高于具体工具。**
2. **Agent 应比用户更了解机器，而不是只模仿用户点击。**
3. **API 和 CLI 优先，UI 操作必须作为完整能力保留。**
4. **目标有歧义时先询问，技术路径有问题时自主解决。**
5. **主 Agent 有行动自主权，但没有自我无限授权权。**
6. **真实世界承诺、不可逆破坏和重大安全变化由用户决定。**
7. **特权变更必须有证据、验证和可信回滚路径。**
8. **秘密不进入模型，云端上下文遵循最小必要原则。**
9. **任务状态属于 Runtime，不依赖单次模型会话。**
10. **主动发现不等于主动处置。**
11. **本地个人 Agent 与可扩展能力平台可以同时成立。**
12. **先证明 Runtime，再决定是否维护发行版。**

## 14. 北极星结果

> 用户可以把一个真实、持续的电脑任务交给 VibeOS，并相信 Agent 会使用
> 最合适的系统或界面能力完成任务；遇到歧义会先询问，遇到风险会正确请
> 求批准，遇到故障能恢复或回滚，最终能用证据说明是否完成。

关键指标包括：

- 黄金任务集端到端完成率；
- 错误完成率；
- 需要用户处理中间技术步骤的频率；
- 长时间任务恢复成功率；
- 特权变更验证和回滚成功率；
- 未经批准的外部或不可逆副作用数量；
- 秘密和私人数据越界数量；
- 主动建议被用户采纳的比例；
- 安装、升级和恢复成功率。

未经批准的外部承诺、重复副作用、秘密进入模型和无法解释的特权操作必须
保持为零。

## 15. 当前阶段判断

当前代码已经拥有 GoalLoop、能力注册、权限审查、持久化审批、执行、验收、
恢复、追踪和审计骨架，但仍是受限桌面 Agent 原型。

与本章程相比，主要缺口是：

- 缺少持续维护的 Machine Model；
- Shell 和系统 API 尚未成为统一受治理的执行面；
- 缺少独立 Reviewer、Privilege Broker 和事务回滚管理器；
- Secret Broker 尚未建立；
- 云端与本地 Context and Model Router 尚未建立；
- 长时间任务的等待、唤醒、重启恢复和用户接管仍不完整；
- 主动发现与建议机制尚未建立；
- 真实 GNOME 桌面闭环和版本化交付仍未完成。

因此，后续工作应围绕这些产品能力推进，而不是继续把现有 capability
executor 当作最终产品形态。

## 16. 产品决策过滤器

任何新需求进入路线图前，至少回答：

1. 它帮助 Agent 理解机器、完成任务还是治理风险？
2. 它解决的是用户目标，还是只增加一个孤立命令？
3. 是否需要用户澄清目标或批准现实世界影响？
4. 最可靠的执行面是 API、CLI、系统服务还是 UI？
5. 需要什么权限，谁审核，权限如何限时和撤销？
6. 动作可回滚、可补偿还是不可逆？
7. 完成条件和证据是什么？
8. 会向哪个模型发送什么数据，是否满足最小必要原则？
9. 任务中断、机器重启或用户接管后如何恢复？
10. 它是否需要发行版能力，还是可以先在现有 Linux Runtime 验证？

无法回答这些问题的需求不能直接进入开发阶段。
