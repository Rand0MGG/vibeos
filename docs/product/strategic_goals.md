# VibeOS 战略目标

状态：已确认战略基线
更新日期：2026-07-15

本文把[产品章程](product_charter.md)转换成可排序、可验收的结果。战略目标
描述“必须取得什么结果”，不直接承诺版本日期或具体实现名称。

## 1. 目标体系

```text
北极星：成为可信的 Agent-native 个人计算层
  |
  +-- G1 建立持续、准确的机器模型
  +-- G2 建立持久化自主任务运行时
  +-- G3 建立 API、CLI 与 UI 统一动作层
  +-- G4 建立提权、秘密、事务与回滚控制面
  +-- G5 建立云端与本地上下文和模型路由
  +-- G6 交付真实 Linux Agent MVP
  +-- G7 建立用户协作与主动建议体验
  +-- G8 建立扩展、交付与发行版演进基础
```

G1 让 Agent 真正了解机器；G2 让它能够持续完成任务；G3 赋予完整执行能
力；G4 和 G5 治理高权限与云端推理；G6 证明真实产品价值；G7、G8 让产
品能够长期使用和扩展。

## 2. G1——建立持续、准确的机器模型

### 目标结果

Agent 不再每次从一句用户请求开始猜测环境，而是拥有对设备、系统、应用、
数据、会话和历史变化的持续理解。

### 必须具备

- 硬件、系统、软件包、应用和版本清单；
- 进程、服务、作业、资源和日志状态；
- 文件、配置、存储、备份和快照索引；
- 网络、设备、账号、权限和当前会话状态；
- 桌面、窗口、应用和浏览器观察；
- 任务、变更、故障和验证结果时间线；
- 数据来源、更新时间、可信度和敏感级别；
- 增量更新、过期失效和按需重新观察机制。

### 成功信号

- Agent 能回答“这台机器现在是什么状态”和“最近发生了什么变化”；
- 规划前能够发现相关依赖、冲突、版本和环境限制；
- 机器重启后仍能恢复必要上下文，但不会把过期状态当成事实；
- 原始敏感内容不会因建立机器模型而被无界复制或永久保留。

### 当前判断

现有观察包只覆盖局部会话信息，尚未形成机器级知识和状态层。

## 3. G2——建立持久化自主任务运行时

### 目标结果

用户给出明确任务后，Agent 可以自主执行数小时，等待外部状态、处理中途
变化、在失败后恢复，并在机器或进程重启后继续。

### 必须具备

- 从自然语言形成可确认的任务契约；
- 对实质歧义、范围和完成条件主动澄清；
- 持久化 Goal、Task、Plan、Attempt、Action 和 Observation；
- 等待、定时唤醒、事件唤醒、暂停、恢复和取消；
- 用户接管、修改目标和重新交还控制；
- 有界重试、修复、重规划和停止策略；
- 预算、超时、成本和资源限制；
- 基于多源证据的 Agent 自主完成判断。

### 成功信号

- 至少一个数小时任务能跨等待和进程重启完成；
- 中断恢复不会重复已确认完成的副作用；
- 目标含义不明确时，系统在行动前提出有效问题；
- 技术路径失败时，Agent 能在任务契约内自主换方案；
- 任务最终状态、停止原因和下一步对用户清晰可见。

### 当前判断

GoalLoop 和审批恢复提供了基础，但持续调度、重启恢复、用户接管和长期任
务治理仍不完整。

## 4. G3——建立 API、CLI 与 UI 统一动作层

### 目标结果

Agent 能使用电脑提供的所有合理操作面，并根据可靠性、效率、风险和可验
证性选择最佳路径。

### 执行优先级

```text
系统或应用 API
  -> CLI 和系统工具
  -> D-Bus / Portal / 系统服务
  -> Accessibility
  -> 结构化 UI 自动化
  -> 鼠标、键盘、截图、OCR 和视觉定位
```

### 必须具备

- 统一的 Action Proposal、执行结果和证据契约；
- Shell 和命令行成为一等、可审计、可限权的能力；
- API、系统工具、Accessibility 和 computer-use 使用相同任务身份；
- 执行面失败后可以降级，但不能扩大原任务影响范围；
- 命令、进程、网络、文件和 UI 副作用可观察；
- 新执行器通过扩展协议接入，不修改核心任务状态机；
- 每个动作都能声明前置条件、效果、权限和完成证据。

### 成功信号

- 同一个目标可以在 API、CLI 和 UI 路径之间安全切换；
- Agent 优先使用结构化高可靠路径，而不是无谓模拟点击；
- 应用没有专用 API 时仍能完成至少一个真实应用内任务；
- Shell 不成为绕过权限、秘密、审计和回滚的旁路。

### 当前判断

当前 capability registry 和工具模块是良好基础，但 Shell 被排除，UI 通用
操作和跨执行面的统一契约尚未建立。

## 5. G4——建立提权、秘密、事务与回滚控制面

### 目标结果

Agent 能够触及系统底层并完成特权任务，但主 Agent 不持有无限 root 权限
或秘密明文；关键操作经过独立审核、限定执行、验证和回滚。

### 必须具备

- 普通任务运行在明确 Sandbox 和用户权限中；
- 结构化 Action Proposal 和 Effect Assessment；
- 静态策略与独立 Reviewer Agent；
- 限定资源、时效和次数的 Privilege Lease；
- 由 Privilege Broker 执行特权动作；
- 可回滚、可补偿、不可逆三类动作语义；
- 配置备份、文件系统快照、包管理事务和健康检查；
- Secret Broker 和不向模型暴露明文的 Secret Reference；
- 用户对外部承诺、不可逆破坏和重大安全变化的最终批准权；
- 所有提权、秘密使用、提交和回滚事件可审计。

### 成功信号

- 主 Agent 无法自行扩大 Privilege Lease；
- 提权审核失败时没有副作用；
- 可回滚系统变更在故障注入后能够恢复并验证；
- 不可逆动作在没有用户批准时无法执行；
- 密码、Token、Cookie 和私钥不进入模型上下文、日志或普通输出；
- 重复审批和并发执行不会产生重复副作用。

### 当前判断

现有 L0–L3 和 ReviewStore 提供审批基础，但缺少系统级提权、独立 Reviewer、
Rollback Manager 和 Secret Broker。

## 6. G5——建立云端与本地上下文和模型路由

### 目标结果

VibeOS 能使用 GPT、DeepSeek 等云端模型获得高质量能力，同时让本地策略
掌握哪些内容可以离开设备、发送多少以及发送给谁。

### 必须具备

- 确定性隐私策略作为硬边界；
- 公开、普通机器元数据、私人内容、秘密和本地限定数据分级；
- 上下文检索、裁剪、结构化、脱敏和本地摘要；
- 基于任务能力、隐私、成本、延迟和可用性的模型选择；
- 云端服务故障时的本地降级和任务暂停策略；
- 不同提供商的数据策略和目标域名控制；
- 用户可理解、可修改的云端使用偏好；
- 记录数据类别、模型、目的和结果，不默认记录原始敏感内容。

### 成功信号

- Secret 等级数据永不进入任何模型；
- 私人内容只有在任务必要且策略允许时才发送；
- Agent 能说明本次为什么选择某个模型、发送了哪类上下文；
- 路由不是完全由待治理的云端模型自行决定；
- 云端不可用不会导致未经声明的隐私降级或无限重试。

### 当前判断

当前支持模型提供商和本地规则回退，但尚未形成独立 Context Router、隐私
分级和多模型选择策略。

## 7. G6——交付真实 Linux Agent MVP

### 目标结果

在现有 GNOME Wayland Linux 上，用户可以安装 VibeOS，并把一个包含系统、
应用和等待过程的真实任务交给 Agent 完成。

### MVP 黄金场景

至少覆盖：

1. Agent 建立本机软件、服务和桌面状态摘要；
2. 使用 API 或 CLI 完成一个无需提权的系统任务；
3. 使用 Privilege Broker 完成一个可回滚的系统配置或软件包任务；
4. 打开应用或网页，并通过 API、系统状态或 UI 证据确认结果；
5. 在无专用 API 的应用中使用 Accessibility 或 UI fallback；
6. 使用 Secret Reference 登录一个测试服务，Agent 不接触明文；
7. 执行一个包含等待、恢复和阶段汇报的长时间任务；
8. 发现一个系统问题并向用户提出建议，由用户决定是否创建修复任务；
9. daemon 重启后恢复任务和审批状态；
10. 对失败的特权变更执行回滚并验证机器恢复。

### 成功信号

- 黄金场景在干净、明确支持的 GNOME VM 中可重复通过；
- 结果来自真实系统和桌面证据，而不是 fake adapter 或 dry-run；
- 安装、启动、任务、提权、秘密、回滚和恢复形成完整链路；
- 每个发布候选都有对应的自动化和人工验收证据；
- WSL 和单元测试不被用来代替真实 Linux 产品结论。

### 当前判断

这是把现有项目重新对准新使命后的首个主要产品里程碑。

## 8. G7——建立用户协作与主动建议体验

### 目标结果

用户管理目标、现实世界决策和授权边界，Agent 管理技术执行。双方通过任
务契约、澄清、阶段汇报、建议和接管建立稳定协作。

### 必须具备

- 目标、范围、完成条件和关键决策的任务契约界面；
- 对模糊请求优先提问，而不是保守拒绝或擅自猜测；
- 简洁的默认状态、阶段进度和最终结果；
- 外部承诺、不可逆动作和重大安全变化的明确批准界面；
- 用户暂停、接管、修改、取消和恢复任务；
- 主动问题发现、证据说明和候选解决方案；
- 默认只提出建议，用户决定是否执行；
- 可配置的长期授权与通知策略，但不得用它绕过 E3 行为的逐次用户批准。

### 成功信号

- 普通用户不需要阅读内部 route、receipt 或巨大 JSON；
- Agent 的澄清问题能够实质减少错误目标；
- 长时间任务不会长时间沉默，阶段汇报不过度打扰；
- 用户能区分“Agent 建议”和“Agent 已经执行”；
- 用户可以在任务中途接管并安全交还控制。

### 当前判断

现有 CLI 和结构化状态适合工程调试，尚未形成目标契约和长期人机协作体验。

## 9. G8——建立扩展、交付与发行版演进基础

### 目标结果

VibeOS 既是设备所有者的本地 Agent，也允许用户按需安装能力、领域知识、
模型和适配器；同时通过版本化交付验证是否需要发展成独立发行版。

### 必须具备

- 核心 Runtime 与能力扩展的稳定边界；
- 扩展声明权限、数据访问、模型使用和副作用；
- 扩展签名、来源、隔离、禁用和升级策略；
- 可重复依赖、版本化包和支持矩阵；
- 安装、升级、卸载、回滚和恢复测试；
- Runtime、桌面桥接和系统服务的兼容性规则；
- 许可证、安全说明、贡献规范和发布记录；
- 发行版决策所需的真实约束和数据记录。

### 发行版启动条件

只有当现有发行版持续阻碍以下能力时，才正式启动 VibeOS Linux：

- 事务式系统变更和可启动回滚；
- Agent 生命周期、权限和秘密的系统级统一；
- 原子更新和版本化机器状态；
- Agent 优先的人机交互和恢复；
- Runtime、桌面和系统服务的一致发布。

### 成功信号

- 用户不需要源码 editable 安装即可使用稳定版本；
- 新能力包不需要修改核心任务状态机；
- 干净环境安装和升级可以重复验证；
- 是否开发发行版由证据和产品收益决定，而不是最初设想决定。

### 当前判断

当前具备 Python 包、CI 和安装脚本基础，但仍是开发态交付和封闭能力集合。

## 10. 实施顺序与阶段门禁

详细实施合同位于
[Agent-native 实施计划](../goals/agent_native/README.md)。九个阶段依次为：

| 顺序 | 阶段 | 主要目标 |
| --- | --- | --- |
| 01 | 核心基础替换 | 建立所有目标共用的分层、持久化和服务生命周期 |
| 02 | Durable Task Engine | G2，以及 G7 所需的等待、恢复和接管基础 |
| 03 | Model Gateway 与 Secret Broker | 收敛 G5 模型调用并建立 G4 的秘密不可见边界 |
| 04 | Machine State 与上下文路由 | G1、G5 的最小可验证数据实现 |
| 05 | E0/E1 Action Fabric | G3 的普通动作、sandbox 和证据闭环 |
| 06 | 特权控制与按操作回滚 | G4 的 Reviewer、polkit 和一个 E2 canary |
| 07 | 桌面 Action Fabric 与 GNOME MVP | G3、G6 和核心 G7 用户协作闭环 |
| 08 | 主动建议与长期协作 | G7 |
| 09 | 扩展、稳定交付与发行版门禁 | G8 |

实施底座和被拒绝的路线由
[决策 0002](decisions/0002-implementation-foundation.md)约束。阶段 05 之前
不得开放通用命令，阶段 06 之前不得开放 root；阶段 07 完成前不得把 WSL、fake
adapter 或 dry-run 写成真实产品证据，也不应扩张多平台、语音、长期记忆或
大量应用能力。发行版工作只能由阶段 09 的正式证据和 ADR 触发。

## 11. 目标治理

每个战略目标后续必须拆成可验收阶段目标，并记录：

- 目标负责人；
- 用户问题和预期结果；
- 基线指标与目标值；
- 范围和明确非目标；
- 依赖、风险和关键假设；
- 数据和模型边界；
- 权限、审批和回滚要求；
- 黄金场景与验收证据；
- 进入条件、退出条件和复审日期；
- 继续、调整或停止决定。

版本计划只能选择这些战略目标的子集，不能另起一套与产品章程冲突的目标。
