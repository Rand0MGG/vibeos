## Detailed Status

### A. Middle-Layer Contract

Status: pass

What is already evidenced:

- Legacy single-intent requests normalize into one-step `TaskPlan` objects.
- `validate_plan()` rejects invalid schema, unknown expected states, and cyclic dependencies.
- Accepted plans include `plan_id`, route id, step ids, provenance, and expected states.
- `display` fields are structurally separated from execution fields.
- Public executor boundaries now reject raw utterance strings and arbitrary payloads; `review_task_plan(...)` and `execute_task_plan(...)` accept only `TaskPlan` objects.
- Invalid plans are rejected at the public entrypoint before review creation or step execution.

### B. Chat vs Task Classification

Status: pass

Evidence in tests:

- `how should VibeOS v0.3 be designed?` -> `chat`
- `open browser` -> `task`
- `explain clipboard permissions and then copy hello to clipboard` -> `mixed`
- `play baby` -> `task`
- `play` -> `clarification`
- `delete downloads` -> `rejected`

### C. Clipboard NL Regression

Status: pass

Evidence in tests:

- `clipboard VibeOS evidence`
- `copy VibeOS evidence`
- `copy to clipboard VibeOS evidence`
- `write VibeOS evidence to clipboard`

All now validate through `plan_payload(...)` to a one-step `clipboard.write` task plan with non-empty `target.text`.

### D. Multi-Step Planning

Status: pass

Evidence in tests:

- `play baby` emits a multi-step media plan.
- The browser fallback route contains ordered dependencies.
- `play` returns clarification and no executable plan.
- When media capabilities are available, route selection can prefer `music_app_route`.
- When media capabilities are not available, route selection chooses `browser_music_search_route`.

### E. Route Selection

Status: pass

What is already evidenced:

- Route scoring is deterministic for the current media candidates.
- Browser fallback wins when media capabilities are absent.
- Music route can win when media capabilities are present.
- When no candidate route satisfies required capabilities, route selection now returns no executable plan.
- Candidate payloads expose `score_inputs`.
- Tie-break tests now cover lower risk, fewer steps, and stable route-id ordering.
- User-facing planner payloads now surface route-level rejection when no satisfiable route exists.

### F. Execution Graph

Status: pass

What is already evidenced:

- Cycles are rejected.
- Failed dependencies block downstream steps.
- Independent safe L0 steps can be grouped into the same execution batch.
- State-changing steps remain sequential even when they share a `parallel_group`.
- Execution results preserve layer information.

### G. Permission Integration

Status: pass

Evidence in tests:

- Every task-plan step receives a permission review.
- L2 steps create stored review records before execution.
- Approving a stored review executes the stored `TaskPlan`, not a fresh natural-language parse.
- Reusing a consumed approval is rejected.
- Audit records include `plan_id`, `step_id`, `review_id`, `layer`, and status.

### H. Adapter Diagnostics Without VM

Status: pass

What is already evidenced:

- Clipboard adapter reports `written` for simulated success.
- Clipboard adapter reports `timeout` for a simulated hanging helper.
- Clipboard adapter reports `unavailable` when no supported helper exists.
- Timeout is exercised without depending on a real `/usr/bin/wl-copy`.
- Notification adapter reports `sent`, `timeout`, and `unavailable` locally with fake subprocess coverage.
- Portal adapter reports `opened`, `timeout`, `unavailable`, and `unsupported` locally with fake subprocess coverage.
- Task-plan step execution now emits typed fields including:
  - `adapter`
  - `capability_id`
  - `attempt`
  - `duration_ms`
  - `adapter_status`
  - `diagnostics`
  - `error_code`
- Broker-level task-plan tests now assert typed adapter metadata for:
  - `app.open`
  - `portal.open_uri`
  - `notification.send`
  - `clipboard.write`

### I. CLI Contract

Status: pass

Evidence in tests:

- `vibe plan "clipboard VibeOS evidence" --json`
- `vibe plan "play baby" --json`
- `vibe ask "clipboard VibeOS evidence" --dry-run --json`
- `vibe ask "explain clipboard permissions and then copy hello to clipboard" --dry-run --json`

Also covered beyond the original acceptance list:

- Normal `vibe ask "open browser" --json` now returns plan-oriented execution metadata.
- Mixed clipboard `vibe ask ... --json` returns stored plan review metadata before execution.

## Follow-On Work

These are reasonable next steps, but they are no longer blockers for the
current acceptance target:

1. Broaden planner-first execution parity across more capability families.
2. Add more daemon and D-Bus end-to-end evidence beyond the current local and HTTP-focused coverage.
3. Use a Fedora GNOME Wayland VM run to validate transport, session, portal, and desktop integration with the current planner-first contract.
