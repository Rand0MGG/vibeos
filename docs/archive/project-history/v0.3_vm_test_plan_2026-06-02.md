# VibeOS v0.3 VM Test Plan

Last updated: 2026-06-02

This document is the operational VM test plan for the current v0.3 state.

It assumes the local A-I acceptance criteria are already green and uses the VM
to validate user-session integration rather than to discover unfinished core
architecture.

## Goal

Verify that the current planner-first runtime works inside a Fedora GNOME
Wayland user session with:

- `vibed.service`
- D-Bus transport
- HTTP daemon status
- GNOME Shell bridge
- planner-oriented `plan` and `ask` flows
- stored review lifecycle
- real desktop-facing side effects where appropriate

## Expected Outcome

A successful VM run should establish:

- user-session daemon is active
- CLI prefers daemon transport instead of silently falling back to local-only execution
- planner-oriented JSON survives the real transport path
- stored review lifecycle works in-session
- desktop integration paths still behave as expected in the VM

This VM run is an integration validation pass. It is not the source of truth
for the core v0.3 local acceptance criteria.

## Preparation

Assume the repository lives at `/home/rand0mg/vibeos`.

From a fresh Fedora GNOME login:

```bash
cd /home/rand0mg/vibeos
source .venv/bin/activate 2>/dev/null || python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
chmod +x scripts/*.sh
./scripts/install_linux_session.sh
```

## Baseline Checks

Run:

```bash
vibe doctor
./scripts/status_linux_session.sh
```

Expected:

- `vibed.service` is active
- `runtime_entry` reports daemon transport rather than local broker
- `org.vibeos.Agent` is visible
- HTTP status endpoint responds
- GNOME extension bridge is healthy if window operations are being tested

## Planner-First CLI Checks

Run:

```bash
vibe plan "clipboard VibeOS evidence" --json
vibe plan "play baby" --json
vibe ask "clipboard VibeOS evidence" --dry-run --json
vibe ask "open browser" --json
vibe ask "explain clipboard permissions and then copy hello to clipboard" --json
vibe reviews pending --json
```

Expected:

- clipboard `plan` returns a one-step `clipboard.write` task plan
- media `plan` returns candidate routes, selected route, ordered steps, and `score_inputs`
- clipboard dry-run returns review-required metadata without touching the clipboard
- `open browser` returns executed task-plan metadata
- mixed clipboard ask returns stored review metadata
- pending reviews show the stored plan review

## Stored Review Lifecycle

After the mixed clipboard request returns a `review_id`, run:

```bash
vibe approve <review_id> --json
vibe reviews pending --json
```

Expected:

- approval executes the stored plan instead of reparsing natural language
- the review record is consumed
- the executed result still includes plan-oriented metadata

## Optional Desktop Integration Checks

If the GNOME bridge is healthy, run:

```bash
vibe ask "open browser" --json
vibe ask "close browser" --json
vibe reviews pending --json
vibe approve <review_id> --json
```

Expected:

- window-targeting actions still work through the session bridge
- review-required actions behave consistently with existing v0.2 daemon behavior

## Evidence Capture

Run:

```bash
python scripts/collect_vm_evidence.py --real
```

Interpretation:

- failures here should now be treated primarily as integration issues
- likely layers are daemon lifecycle, desktop session, portal bridge, clipboard helper, or GNOME Shell bridge
- they should not automatically be interpreted as unfinished v0.3 architecture work

## Pass / Fail Interpretation

Pass:

- daemon and transport checks are healthy
- planner-oriented JSON appears in the VM exactly as it does locally
- stored review lifecycle works
- desktop-facing commands that are already supported by the VM environment behave consistently

Fail:

- daemon is unavailable
- planner-oriented payload is lost across transport
- stored approval path reparses or loses plan metadata
- GNOME or portal integration breaks expected session behavior

When failures occur here, the next debugging target should usually be VM
integration or desktop environment behavior, not the already-accepted local
v0.3 architecture.
