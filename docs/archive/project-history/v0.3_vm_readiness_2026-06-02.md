# VibeOS v0.3 VM Test Readiness

Last updated: 2026-06-02

This document is a practical VM-readiness note for the current v0.3 work.

It is not the design document. It exists so VM testing can be scheduled with a
clear understanding of what is worth testing now and what is still better kept
as local-only verification.

## Current Recommendation

Recommended status: ready for direct VM integration testing.

Reason:

- The local A-I acceptance criteria are now complete.
- The remaining work is primarily transport, session, portal, and desktop integration validation.
- A VM run is now useful as a direct integration test of the accepted planner-first runtime.
- Per the v0.3 plan document, VM success is not the core definition of done for v0.3 local architecture work.

## What Is Ready To Smoke Test In A VM

These paths now have enough local evidence that a VM run is meaningful:

- `vibe plan "<utterance>" --json`
- `vibe ask "open browser" --json`
- `vibe ask "clipboard VibeOS evidence" --dry-run --json`
- `vibe ask "explain clipboard permissions and then copy hello to clipboard" --json`
- review lifecycle through HTTP daemon:
  - request
  - pending review visibility
  - approval of stored task plan
  - consumption of the review record

## What The VM Should Validate Now

- daemon and session lifecycle in Fedora GNOME Wayland
- transport parity across the real user session
- GNOME Shell bridge behavior
- portal and clipboard helper behavior in the desktop environment
- planner-first request, review, and approval behavior under real session conditions

## Local Evidence Snapshot

Current evidence:

- `conda run -n vibeos python -m pytest -q`
- Result: `143 passed, 1 warning`

Key areas already covered locally:

- public `TaskPlan` executor boundaries reject raw utterances and invalid plans before review or execution
- planner analysis and route selection
- no-plan outcome when no route satisfies required capabilities
- deterministic route tie-break behavior for current candidate plans
- safe parallel-group scheduling for eligible execution-graph batches
- stored `TaskPlan` reviews
- normal `ask` execution through the task-plan path
- HTTP daemon lifecycle for stored plan approvals
- transport serialization of nested plan metadata
- clipboard, portal, and notification adapter success or open, timeout, unavailable, and unsupported helper cases where applicable
- current local acceptance status document marks A-I as pass

## Suggested VM Test Now

Use:

1. `vibe doctor`
2. `./scripts/status_linux_session.sh`
3. `vibe plan "play baby" --json`
4. `vibe ask "open browser" --json`
5. `vibe ask "clipboard VibeOS evidence" --dry-run --json`
6. `vibe ask "explain clipboard permissions and then copy hello to clipboard" --json`
7. `vibe reviews pending --json`
8. `vibe approve <review_id> --json`

Interpretation:

- If VM-only breakage appears here, it is likely a transport, session, portal, clipboard-helper, or desktop-integration issue.
- If these all pass, the current planner-first runtime is behaving correctly in the VM integration layer.

## Readiness Conclusion

- The current codebase is ready to be tested directly in a VM.
- VM results should now be interpreted as integration evidence, not as a substitute for the local A-I acceptance suite.
- For a step-by-step command list, use `docs/v0.3_vm_test_plan_2026-06-02.md`.
