# VibeOS v0.6 Goal For Codex

## Overview

This document is the implementation brief for **VibeOS v0.6: agent shell runtime, generalized tool architecture, and durable goal orchestration**.

v0.5 completed the typed task pipeline:

- typed goal synthesis
- explicit supported-task domains
- explicit acceptance
- explicit debug trace
- bounded run and attempt metadata

That was the right step for tightening correctness, but it still leaves VibeOS in the shape of a **typed capability executor**.

v0.6 must change the product shape.

v0.6 should not be framed as:

- more Linux desktop commands
- more browser heuristics
- more route-specific replanning rules
- more special cases for individual targets

v0.6 should be framed as:

**VibeOS becomes an agent runtime control plane, while Linux desktop and browser control remain the first core capability surfaces.**

The design target is closer to mature systems such as Codex CLI, Claude Code, and Hermes:

- a persistent goal-oriented loop
- explicit runtime state
- clear separation between planning, acting, observing, and judging
- multiple tool families, not only side-effect tools
- bounded recovery with durable run history
- exit conditions based on outcome, not just on command dispatch

v0.6 must solve root causes. It must not be implemented as a pile of domain patches.

## Goal Prompt

Your goal is to implement VibeOS v0.6 on top of the existing v0.5 architecture.

v0.6 must transform VibeOS from a request-to-plan executor into a **session-based agent runtime** that can:

- hold a goal across multiple turns and multiple strategies
- choose tools from multiple tool families
- continue after partial failure using structured evidence
- stop only because the runtime reached a justified terminal state
- expose the full run state to the user and to Codex

The design target is:

```text
user session
  -> goal runtime
  -> strategy candidates
  -> strategy selection
  -> tool orchestration
  -> action / observation / verification
  -> outcome evaluation
  -> continue / retry / replan / ask user / stop
  -> durable run ledger
```

Linux session integration remains a first-class product surface. The architectural center moves to the agent runtime loop, but the first proof of that loop must still be anchored in current desktop and browser capabilities.

## Product Repositioning

v0.6 should explicitly reposition VibeOS from:

- a Linux session task broker

to:

- a local agent runtime control plane whose first core capability surface is Linux desktop and browser control

Examples of capability surfaces that should fit this shape:

- browser tools
- Linux desktop tools
- observation and verification tools
- future workspace-local tools
- future shell-local tools

The runtime should not assume that desktop actions are the only possible product surface. It also must not treat desktop control as optional or incidental in v0.6.

## Root Cause Statement

The most important current problem is not that one browser flow is imperfect.

The real problem is that the system still compresses a natural-language request into an executable action plan too early.

That early compression creates recurring pathologies:

- strategy mistakes are treated like execution mistakes
- a goal can disappear when a route fails
- the runtime has too few tool types, so it overuses action tools as if they were reasoning tools
- completion can still drift too close to "the command was dispatched"
- replanning remains too tied to handwritten domain exceptions

These are structural problems.

v0.6 must solve them structurally.

## Design Principles

v0.6 must follow these principles.

### 1. Goal is not strategy

The user goal must remain stable while strategies change.

### 2. Strategy is not action

A strategy is a way to pursue the goal. It is not yet an executable step sequence.

### 3. Action is not completion

The runtime must not treat adapter dispatch as goal completion when the domain needs verification or observation.

### 4. Non-action tools are first-class

Resolvers, observers, verifiers, and wait/poll tools must participate in the main loop as first-class runtime tools.

### 5. Runtime state is inspectable

The user and Codex must be able to inspect:

- current goal
- current strategy
- executed attempts
- evidence collected
- outcome classification
- stop reason

### 6. Recovery is bounded and principled

Retry and replan must be driven by structured policy, not by ad-hoc domain fallbacks.

### 7. Environment is part of planning

The runtime must plan and replan with explicit environment knowledge instead of hiding environment assumptions inside domain logic.

### 8. Use mature patterns only

v0.6 must not introduce speculative agent architecture.

New runtime concepts must satisfy at least one condition:

- they are required by the v0.6 minimal vertical slice
- they directly preserve an existing v0.5 contract such as `GoalSpec`, `TaskPlan`, review, acceptance, audit, or debug trace
- they mirror a mature pattern already proven in systems such as Codex, Claude Code, or Hermes: isolated execution boundaries, explicit tool availability, scoped context, structured task state, permission gates, and inspectable progress

If a concept cannot be justified this way, it should not be implemented in v0.6.

### 9. Root cause first, no patch branches

When v0.6 encounters a failure mode, the implementation must classify the root cause before adding behavior.

Allowed fixes:

- add or tighten a reusable runtime policy
- improve strategy selection with structured evidence
- improve tool-family boundaries
- improve observation, verification, or outcome classification
- return a structured blocked or unsupported result

Disallowed fixes:

- ad-hoc route fallback for one target
- hidden legacy fallback that makes the test pass
- pretending weak evidence is success
- adding a new tool surface because one scenario is inconvenient
- swallowing provider, environment, or observation failure and continuing as if nothing changed

## Scope Decision

v0.6 must prioritize system-wide leverage.

The primary scope is:

1. session-based runtime
2. durable goal lifecycle
3. strategy layer
4. layered tool protocol
5. durable run ledger
6. environment-aware orchestration
7. generalized outcome policy

The primary non-scope is:

- shipping many more domain-specific tricks
- expanding desktop-specific capability breadth without fixing the runtime core

Engineering discipline:

- solve root causes at the runtime-policy or tool-protocol layer, not by accumulating one-off domain patches
- prefer a structured `blocked`, `unsupported`, or `needs_user_input` outcome over a misleading partial success
- do not widen the capability surface to make one test easier
- do not accept tests that pass only because a fallback hides the real failure layer

## v0.6 Minimal Vertical Slice

v0.6 must prove the new runtime with one concrete vertical slice before broadening the framework.

The first slice must be anchored in current capability surfaces, preferably `apps` plus `browser`. It must not require real file operations, real shell commands, a real browser session, a real VM, or live network access.

Recommended deterministic scenario:

```text
user goal: "open Notion"

strategy candidate A:
  use desktop app resolution and app.open
  resolver evidence: no installed app match in fake app catalog
  outcome: strategy rejected or attempt incomplete due semantic mismatch

strategy candidate B:
  use browser search or browser URL route as fallback
  observer evidence: fake browser observation reports expected URL or query
  verifier evidence: browser verifier accepts the observed result
  outcome: completed
```

Required properties of the slice:

- one `AgentSession` owns one stable goal id
- the goal produces at least two `StrategyCandidate` objects
- the first strategy fails, is rejected, or produces indeterminate acceptance without changing the goal id
- `RecoveryPolicy` selects the second strategy using structured do-not-repeat or failure-class constraints
- at least one resolver tool participates in the first strategy
- at least one action tool participates in each attempted strategy
- at least one observer tool participates before final acceptance
- at least one verifier tool participates before final acceptance
- `RunLedger` records session id, goal id, strategy decisions, attempts, evidence, recovery decision, and terminal outcome
- all evidence is supplied by deterministic local fixtures

This slice is the hard proof that v0.6 is not just a set of runtime dataclasses. Do not count v0.6 as healthy until this slice passes end to end.

## Codex / WSL Acceptance Boundary

v0.6 acceptance must stay inside work Codex can complete in the repository or in WSL.

Codex-owned acceptance may include:

- repository-local unit and integration tests
- deterministic fake provider, fake resolver, fake observer, and fake verifier fixtures
- `pytest -q`
- CLI JSON contract checks with `--offline` and `--dry-run`
- WSL user-space pre-validation as described in `docs/zh_cn/07_wsl_test_standard.md`
- WSL checks for Python packaging, imports, executable entrypoints, Linux path behavior, and structured CLI output
- WSL `vibe doctor --json` checks interpreted according to WSL's role, where missing GNOME or portal pieces may be expected `warn` rather than failure

Codex-owned acceptance must not require:

- Fedora GNOME VM access
- real GNOME Shell extension behavior
- real Wayland window management
- real desktop notifications
- real clipboard mutation
- real browser window state
- real `xdg-desktop-portal` success
- live network access
- `python scripts/collect_vm_evidence.py --real`

VM validation is a separate user-owned integration phase. v0.6 local completion means the runtime architecture and deterministic WSL-safe behavior are correct; it does not claim that real VM desktop integration has passed.

## Prerequisite Gate

Do not start v0.6 implementation until the v0.5 local baseline is healthy.

Required baseline:

- `pytest -q` passes locally
- v0.5 supported-task migration tests pass
- goal synthesis tests pass
- acceptance engine tests pass
- debug trace tests pass
- public JSON still exposes `execution_status`, `acceptance_status`, and `overall_status`
- `vibe ask "search web for hello" --json --offline --dry-run` returns structured output without traceback

If this gate fails, fix the v0.5 regression first. Do not hide a v0.5 regression behind new v0.6 runtime abstractions.

## Architecture Target

### 1. Session-Based Runtime

v0.6 must introduce a runtime centered on a persistent session rather than a single-shot command result.

At minimum, the architecture should model:

- `AgentSession`
- `GoalRuntime`
- `GoalTurn`
- `RunLedger`
- `AttemptLedgerEntry`
- `TerminalOutcome`

Requirements:

- one user session can contain multiple goals
- one goal can span multiple turns
- one turn can produce multiple attempts
- the user can continue a goal rather than always creating a brand-new one

This is the foundation for becoming more like Codex CLI.

### 2. Strategy Layer

v0.6 must introduce an explicit strategy layer between `GoalSpec` and executable `TaskPlan`.

Suggested concepts:

- `StrategyCandidate`
- `StrategyConstraint`
- `StrategySelection`
- `StrategyDecision`
- `RecoveryPolicy`

The strategy layer must own:

- alternate ways to pursue a goal
- policy-aware route preference
- fallback choice
- clarification choice
- bounded replanning

The runtime must be able to say:

- keep the goal
- reject this strategy
- select another strategy

without pretending that the goal itself changed.

### 3. Layered Tool Protocol

v0.6 must define a general tool protocol and classify tools by family.

At minimum:

- `action tools`
- `resolver tools`
- `observer tools`
- `verifier tools`
- `wait/poll tools`
- `environment tools`

This classification must not be cosmetic.

The runtime must actually use it for:

- planning
- execution
- replanning
- debug trace
- audit
- local testing

Desktop adapters should become one subset of `action tools`, not the whole runtime model.

### 4. Generalized Capability Surfaces

v0.6 should begin modeling multiple capability surfaces.

At minimum, the runtime protocol should be able to describe the existence of:

- `workspace-local`
- `shell-local`
- `browser`
- `desktop-linux`

Implementation boundary:

- `desktop-linux` and `browser` are the only required semantic capability surfaces for the v0.6 minimal vertical slice.
- The slice may execute through fake, dry-run, or local fixture adapters. It must not require real desktop or browser side effects.
- `workspace-local` and `shell-local` may exist only as typed placeholders or future surface descriptors.
- v0.6 must not introduce general file mutation, general shell execution, or arbitrary process control.
- Any workspace or shell examples in tests must be fake, read-only, or dry-run-only unless a later document explicitly expands the safety model.

The runtime architecture must stop assuming a single desktop-centric action plane, but the implementation must not expand into a general shell or file agent in v0.6.

### 5. Unified Observation and Verification Pipeline

Observation and verification must become a generalized pipeline, not a browser-special subsystem.

The runtime must distinguish:

- actions that complete immediately on success
- actions that need post-action observation
- actions that need delayed or repeated observation
- actions that require user confirmation when evidence stays weak

This must be modeled in runtime policy, not patched in one domain.

### 6. Outcome-Driven Agent Loop

The loop must be driven by structured outcome states.

Suggested outcome states:

- `completed`
- `incomplete`
- `failed`
- `blocked`
- `needs_user_input`
- `needs_review`
- `retryable`
- `replannable`

The runtime should continue only when the outcome policy says to continue.

It should stop only when the outcome policy says to stop.

This is the core behavior change that makes the system more like a mature CLI agent runtime.

### 7. Durable Run Ledger

The run ledger must become a first-class runtime artifact.

Every run should preserve:

- session id
- goal id
- strategy history
- selected strategy
- action-plan history
- attempt history
- evidence history
- failure classifications
- recovery decisions
- terminal stop reason

The ledger must serve four roles:

- runtime state
- debug surface
- audit surface
- replanning input

### 8. Environment Profile

v0.6 must add a first-class environment profile.

At minimum it should capture:

- platform
- transport mode
- daemon availability
- desktop integration availability
- connectivity limitations
- region or deployment profile
- search or navigation policy

The runtime should use this profile during:

- strategy selection
- action planning
- recovery decisions
- tool availability checks

This should not live as scattered conditionals in unrelated modules.

### 9. Provider and Planning Boundary

v0.6 must keep the provider boundary explicit and testable.

The runtime should support:

- deterministic local strategy generation
- model-assisted strategy generation
- model-assisted clarification
- future subagent planning

without silently collapsing back into opaque rule behavior.

If a provider is unavailable, the runtime should surface a structured planning limitation rather than pretend that nothing changed.

## Required New Runtime Concepts

v0.6 must add explicit typed representations for concepts that are still partial or implicit in v0.5.

Suggested required models:

- `AgentSession`
- `GoalRuntime`
- `GoalPolicy`
- `StrategyCandidate`
- `StrategyDecision`
- `RecoveryPolicy`
- `ToolInvocationEnvelope`
- `ObservationEvidence`
- `VerificationEvidence`
- `EnvironmentProfile`
- `RunLedger`
- `AttemptLedgerEntry`
- `OutcomeDecision`

Exact names may differ, but the concepts must exist.

## Behavioral Requirements

By the end of v0.6, the repository should satisfy all of the following local behaviors.

### A. Goals survive strategy replacement

The same goal id can persist across multiple strategy attempts.

### B. Strategies survive action failure

The runtime can reject or replace an action plan without discarding the goal.

### C. Non-action tools participate in the main loop

Local runs can invoke resolver, observer, and verifier tools as part of normal orchestration.

### D. Session state is first-class

The system can expose session or goal runtime state instead of only exposing one-shot command results.

### E. Terminal states are justified

Every stopped run exposes a structured stop reason.

### F. Recovery is policy-driven

Retry and replan decisions come from structured runtime policy rather than domain-specific patch branches.

### G. Environment affects strategy

Different environment profiles can change strategy preference or block unsafe or unproductive strategies.

## Local Acceptance Criteria

v0.6 counts as complete for Codex only if all of the following are true in the local repository and, when available, WSL. These are not VM acceptance criteria.

### 1. Full automated test pass

`pytest -q` passes locally in the intended development environment.

If WSL is available, Codex should also be able to run the WSL-safe subset described in `docs/zh_cn/07_wsl_test_standard.md`:

- `python -m pytest -q`
- `vibe doctor --json` with WSL-appropriate `warn` handling
- `vibe ask "search web for hello" --json --offline --dry-run`

Do not require VM-only commands for v0.6 completion.

### 2. Minimal vertical slice passes end to end

Local tests prove the minimal vertical slice described above:

- one stable goal id survives two strategy attempts
- the first strategy records resolver evidence and a structured failure or indeterminate outcome
- recovery policy selects a second strategy without changing the goal
- resolver, action, observer, and verifier tools all participate in the run
- the final terminal outcome is justified by verifier evidence
- `RunLedger` exposes the complete goal, strategy, attempt, evidence, recovery, and terminal outcome chain
- no test depends on real shell execution, file mutation, VM state, browser state, or network access
- the same behavior can be exercised with local fixtures in a WSL-safe way

### 3. Session runtime has typed local coverage

Local tests prove:

- a session can own one or more goals
- one goal can survive multiple turns
- one goal can preserve a stable goal id across multiple attempts

### 4. Strategy layer has typed local coverage

Local tests prove:

- one goal can produce multiple strategy candidates
- a strategy can be rejected without changing the goal
- a replacement strategy can be selected using do-not-repeat constraints

### 5. Tool-family separation has local coverage

Local tests prove:

- at least one resolver tool participates in a run
- at least one observer tool participates in a run
- at least one verifier tool participates in a run
- action tools remain independently auditable

### 6. Outcome-driven loop has local coverage

Local tests prove:

- action success does not imply goal completion when observation is required
- observation can advance a goal to completion
- missing evidence can keep a goal incomplete
- structured failure can trigger retry or strategy replacement
- bounded recovery still terminates deterministically

### 7. Environment profile has local coverage

Local tests prove:

- strategy selection can read environment profile inputs
- tool availability can be constrained by environment profile
- different environment profiles can prefer different strategies

### 8. Run ledger has complete structured coverage

Local tests prove the run ledger records:

- session id
- goal id
- attempt ids
- strategy decisions
- evidence
- failure classification
- terminal stop reason

### 9. Debug surfaces remain inspectable

Local tests prove debug mode exposes:

- goal runtime
- strategy candidates
- selected strategy
- action-plan provenance
- recovery decisions
- provider artifacts when used

## Recommended Implementation Order

Codex should implement v0.6 in this order:

1. write failing local tests for the minimal vertical slice
2. define only the session, strategy, tool-envelope, outcome, and ledger models needed by that slice
3. route existing `apps` and `browser` capabilities through the minimal tool-family protocol
4. implement the minimal outcome-driven loop for the slice
5. add environment profile only to the extent needed to affect strategy selection in the slice
6. wire resolver, action, observer, and verifier fixtures into the same run
7. make the run ledger the source of truth for strategy decisions, evidence, recovery, and terminal outcome
8. expand coverage only after the minimal slice proves the runtime improvement
9. update documentation and operational guidance

Do not start by building a complete generic agent framework. The first implementation must prove a concrete goal survives strategy failure and reaches a justified terminal outcome.

## Documentation Maintenance During Implementation

Codex must maintain implementation documentation while coding.

Allowed documentation updates:

- update current status docs with implemented v0.6 pieces
- add or update architecture notes that describe the actual code shape
- record local test evidence and WSL-safe verification evidence
- document new public JSON fields, CLI examples, and debug/ledger payloads
- document known limitations that remain outside v0.6 scope

Disallowed documentation changes:

- do not weaken this v0.6 goal during implementation
- do not remove or soften the minimal vertical slice requirement
- do not move VM-only work into Codex-owned acceptance
- do not broaden v0.6 into real shell/file mutation or plugin execution
- do not edit this goal document to match an incomplete implementation

If implementation reveals that the v0.6 goal is wrong or impossible, stop and report the blocker. Do not silently change the goal to make the work look complete.

## Non-Goals

The following are explicitly not required for v0.6 completion:

- solving every browser or desktop edge case
- adding arbitrary remote plugin execution as a hard dependency
- implementing real general-purpose shell execution
- implementing real general-purpose file mutation
- implementing a plugin marketplace or dynamic tool installation system
- becoming a full autonomous web agent
- becoming a full IDE replacement in one release
- shipping complete long-horizon autonomy across hours or days
- replacing the permission review model
- requiring a real Fedora VM for local acceptance
- requiring Codex to prove real GNOME desktop behavior
- requiring WSL to substitute for VM desktop acceptance
- claiming completion from dataclass coverage without the minimal vertical slice

## Migration Guidance

v0.6 should reuse and evolve v0.5 assets rather than discarding them.

Specifically:

- `GoalSpec` should remain the typed representation of synthesized user intent
- `TaskPlan` should remain the executable action-plan layer
- `run` and `attempts` should evolve into the fuller run ledger
- the acceptance engine should evolve into a generalized outcome subsystem
- debug trace should expand to include strategy and session artifacts

## Completion Standard

Do not count v0.6 as complete if:

- VibeOS still behaves primarily as a one-shot request executor
- the minimal vertical slice does not pass end to end
- strategy is still fused directly into domain plan builders
- non-action tools are still absent from the main runtime loop
- terminal status still mostly means "one adapter returned"
- recovery still depends mostly on handwritten domain-specific exceptions
- Linux desktop control still implicitly defines the entire product
- Linux desktop and browser control are no longer treated as the first core capability surfaces
- v0.6 introduces general shell or file mutation capability as part of the required path
- runtime abstractions exist but do not improve a concrete goal outcome compared with v0.5
- completion depends on VM-only evidence or real desktop side effects that Codex cannot produce

v0.6 is complete for Codex when the local codebase proves, through the minimal vertical slice, local deterministic tests, and WSL-safe checks where available, that VibeOS has become a **session-based, goal-driven, strategy-aware, tool-rich local agent runtime control plane** whose first core capability surfaces remain Linux desktop and browser control. Real VM desktop validation remains a separate user-run integration phase.
