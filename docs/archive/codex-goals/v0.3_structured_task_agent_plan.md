# VibeOS v0.3 Structured Task Agent Plan

Last updated: 2026-06-02

## Executive Summary

VibeOS v0.3 moves from "natural language to one intent" to a typed, inspectable, and testable pipeline:

```text
user utterance
  -> utterance analysis
  -> candidate task plans
  -> route selection
  -> plan validation
  -> permission review
  -> execution graph scheduler
  -> capability adapters
  -> evidence and audit
```

The main output of the natural-language layer is no longer a single `Intent`. It is a `TaskPlan` containing one or more typed `TaskStep` objects, with explicit dependencies, route score inputs, risk metadata, expected states, and structured provenance.

Hard rule: execution, permission review, routing, and audit assertions must depend on typed fields, not free-form explanation text. Human-readable fields are display-only.

This directly addresses the latest evidence split:

- `real_clipboard_review_required` failed because natural-language parsing did not reliably produce `clipboard.write`.
- `real_clipboard_adapter_direct` separately proved the Wayland clipboard adapter path can hang on `/usr/bin/wl-copy`.
- `real_clipboard_approve` was correctly marked `blocked` because no `review_id` existed.

v0.3 must preserve that diagnostic separation. NL parse failures, plan and permission failures, and adapter execution failures should be independently observable.

## Middle Layer Contract

v0.3 should be treated as a durable middle-layer contract, not just a planner feature:

```text
UtteranceAnalysis -> CandidateTaskPlans -> ValidatedTaskPlan -> ReviewedTaskPlan -> PlanExecutionResult
```

Only `ValidatedTaskPlan` and stored reviewed plan or step records may enter execution. Raw natural language, chat text, route explanations, model prose, and unvalidated candidate plans must never enter execution.

Core invariants:

- One execution input: executors consume `TaskPlan` or `TaskStep`, never raw user text.
- One validation gate: schema, capability, target, route, and DAG checks must pass before permission review.
- One permission boundary: permission review runs after validation and before adapter execution.
- One audit shape: every result records `plan_id`, `step_id`, `layer`, `status`, and structured failure cause.
- One compatibility path: legacy single `Intent` commands are internally normalized into one-step `TaskPlan` objects.

## Display Fields Policy

Human-readable fields should live under `display`:

```json
{
  "display": {
    "goal": "open a browser",
    "explanation": "A single-step app route satisfies the request.",
    "assumptions": []
  }
}
```

`display.goal` is for user-facing confirmation. `display.explanation` is for audit and debug readability. `display.assumptions` is optional and display-only.

These fields must never influence:

- capability selection
- target values
- permission review
- route scoring
- execution order
- adapter payloads
- test assertions

Required structured fields:

- `type`
- `confidence`
- `task_spans`
- `action`
- `target`
- `depends_on`
- `route_id`
- `score_inputs`
- `risk_level`
- `capability_id`
- `preconditions`
- `expected_state`
- `provenance`

## Expected State Registry

`expected_state` is the machine-checkable success target for a step. Each kind should be registered by capability or execution domain.

Example:

```json
{
  "expected_state": {
    "kind": "clipboard_content_requested",
    "text": "hello"
  }
}
```

Minimum v0.3 registry:

- `app_list_requested`
- `app_opened_or_focused`
- `window_list_requested`
- `window_state_requested`
- `system_status_requested`
- `clipboard_content_requested`
- `uri_open_requested`
- `notification_requested`
- `search_results_available`
- `media_playing`

Validation rules:

- Unknown `expected_state.kind` rejects the plan before permission review.
- Required keys for each `kind` are schema-checked.
- Tests assert `expected_state.kind` and required keys, not display text.

## Strong Provenance

`provenance` must be structured. It should identify where the decision came from and which part of the user text produced it.

Rule fast-path example:

```json
{
  "parser": "rule_fast_path",
  "parser_version": "v0.3",
  "source_span": {"start": 0, "end": 26, "text": "clipboard VibeOS evidence"},
  "model": null,
  "repair_applied": false,
  "confidence": 0.98
}
```

Schema-model example:

```json
{
  "parser": "schema_model",
  "parser_version": "v0.3",
  "source_span": {"start": 0, "end": 9, "text": "play baby"},
  "model": "deepseek-v4-flash",
  "schema_version": "v0.3",
  "repair_applied": false,
  "confidence": 0.84
}
```

## Layer Responsibility Boundaries

`UtteranceClassifier`:

- Decides only `chat`, `task`, `mixed`, `clarification`, or `rejected`.
- May split task spans.
- May assign broad domains and confidence.
- Must not create executable actions, routes, or targets.

`TaskPlanner`:

- Converts each task span into one or more candidate plan skeletons.
- May create candidate steps with action names and target slots.
- May create candidate routes from known templates.
- Must not choose the final route based on runtime availability.
- Must not invent new semantics after the classifier has scoped the task span.

`RouteSelector`:

- Scores already-formed candidate routes.
- May use capability availability, risk, preconditions, and deterministic preference rules.
- Must not create new actions, new targets, or new step semantics.
- Must return score inputs so route decisions are inspectable.

`PlanValidator`:

- Rejects malformed or unsafe plan structures before permission review.
- Must not repair plans by inventing new actions or changing targets.
- May emit warnings for non-fatal display or route-quality issues.

This boundary keeps bugs diagnosable: a bad type is classifier failure, a bad step skeleton is planner failure, a bad route choice is selector failure, and a failed subprocess is adapter failure.

## Validation Gate

Add a `PlanValidationResult` that runs before permission review:

```json
{
  "ok": true,
  "plan_id": "plan_...",
  "errors": [],
  "warnings": []
}
```

The validation gate checks:

- schema version is supported
- ids are unique and stable
- selected route exists
- every selected route step exists
- every action maps to a registered capability
- every target passes capability target schema
- every dependency references an existing step
- dependency graph is acyclic
- every `expected_state.kind` is registered
- every step has structured provenance
- `display` fields stay under length caps

If validation fails, permission review and execution must not run.

## Route Scoring Contract

Route selection must be deterministic for the same inputs.

Route score should be calculated from structured inputs:

```json
{
  "score_inputs": {
    "domain_match": 1.0,
    "capability_coverage": 1.0,
    "precondition_score": 0.8,
    "risk_penalty": 0.25,
    "clarification_penalty": 0.0,
    "preference_bonus": 0.0
  },
  "score_formula": "domain_match*0.35 + capability_coverage*0.30 + precondition_score*0.20 + preference_bonus*0.05 - risk_penalty*0.10 - clarification_penalty*0.20"
}
```

Tie-break order:

1. higher score
2. lower maximum risk level
3. fewer missing preconditions
4. fewer steps
5. stable route id sort

The selector may reject all routes or request clarification, but it cannot invent a new route.

## Deterministic Fast Path Boundary

The deterministic layer is not a Siri-style command system. It is a narrow fast path for inputs where the schema mapping is obvious and high-value for regression stability.

Allowed uses:

- normalize frequent aliases into typed fields
- protect known fragile commands such as `clipboard VibeOS evidence`
- bypass model variance for narrow commands with exact slots
- generate provenance as `rule_fast_path`

Disallowed uses:

- broad open-ended semantic interpretation
- inventing multi-step routes from vague user goals
- replacing the planner
- encoding long lists of product-specific commands that cannot be maintained

## Goal 1: Distinguish Chat, Task, Mixed, and Clarification

Add a front-door classifier that returns a typed `UtteranceAnalysis`. The classifier must not emit executable action names.

Example:

```json
{
  "utterance": "play baby",
  "type": "task",
  "confidence": 0.86,
  "domains": ["media"],
  "explanation": "The user expresses a media playback goal.",
  "task_spans": [
    {
      "id": "span_1",
      "text": "play baby",
      "start": 0,
      "end": 9,
      "domain": "media",
      "confidence": 0.86
    }
  ],
  "provenance": {
    "parser": "schema_model",
    "parser_version": "v0.3",
    "source_span": {"start": 0, "end": 9, "text": "play baby"},
    "confidence": 0.86
  },
  "chat_response": null
}
```

Recommended types:

- `chat`
- `task`
- `mixed`
- `clarification`
- `rejected`

Rule: only `task` and task portions of `mixed` can reach the planner.

Additional hard rule for `mixed`: the chat response must never affect capability choice, target values, permission outcome, or route selection. It is display-only.

## Goal 2: Convert Natural Language Into a TaskPlan

Replace single-intent parsing with a plan schema.

Example:

```json
{
  "schema_version": "v0.3",
  "plan_id": "plan_...",
  "utterance": "open browser",
  "display": {
    "goal": "open a browser",
    "explanation": "A single-step app route satisfies the request.",
    "assumptions": []
  },
  "status": "planned",
  "source_span_id": "span_1",
  "selected_route_id": "app_open_route",
  "routes": [
    {
      "id": "app_open_route",
      "score": 1.0,
      "display": {"explanation": "The app route directly satisfies the request."},
      "score_inputs": {
        "domain_match": 1.0,
        "capability_coverage": 1.0,
        "precondition_score": 1.0,
        "risk_penalty": 0.1,
        "clarification_penalty": 0.0,
        "preference_bonus": 0.0
      },
      "required_capabilities": ["app.open"]
    }
  ],
  "steps": [
    {
      "id": "step_app_open",
      "action": "app.open",
      "capability_id": "app.open",
      "target": {"name": "browser"},
      "depends_on": [],
      "risk_level": "L1",
      "parallel_group": "g1",
      "expected_state": {"kind": "app_opened_or_focused", "fields": {"app": "browser"}},
      "preconditions": [{"kind": "capability_available", "capability_id": "app.open"}],
      "provenance": {"source_span_id": "span_1", "planner": "app_template"}
    }
  ],
  "provenance": {
    "planner": "TaskPlanner",
    "planner_version": "v0.3",
    "source_span_id": "span_1"
  },
  "needs_user_input": false
}
```

`expected_state` is the machine-checkable success target. `display.goal`, `display.explanation`, and `display.assumptions` are display-only and must not drive execution.

v0.3 does not need full media-app automation. It does need the schema, planner, route scoring, fake execution tests, and a browser fallback route that can be dry-run locally.

## Goal 3: Select a Route When Multiple Implementations Exist

Add a `RouteSelector` that ranks already-formed routes using explicit signals:

- capability availability
- risk level
- user domain intent
- current environment state
- route completeness
- need for clarification
- deterministic preference rules

The selector cannot add steps or rewrite targets. If every route is invalid, it returns `needs_user_input` or `rejected` with structured failure causes.

Example route ranking for `play baby`:

1. `music_app_route`
2. `browser_music_search_route`
3. `local_file_search_route`

Do not choose a route purely because the LLM wrote it.

## Goal 4: Execute a Plan, Not a Sentence

Add an `ExecutionGraph` scheduler:

- Validate step ids are unique.
- Validate dependencies form a DAG.
- Run independent read-only or safe L0 steps in parallel.
- Run state-changing L1 and L2 steps sequentially unless a capability declares `parallel_safe=true`.
- Stop or mark downstream steps `blocked` when dependencies fail.
- Preserve root-cause classification.

Execution states:

- `pending`
- `running`
- `succeeded`
- `failed`
- `blocked`
- `needs_user_input`
- `rejected`

## Goal 5: Keep Permission Review Between Plan and Execution

Permission review should support both step-level and plan-level summaries.

Rules:

- Every step maps to a registered capability.
- Unknown capabilities become L3 and reject or force route fallback.
- L2 steps create stored review records before execution.
- Approval executes the stored `TaskPlan` or stored `TaskStep`, not a fresh parse.
- The review payload must show route, step, target, expected effect, and risk.

## Goal 6: Preserve Layered Diagnostics

Every evidence step should report a `layer`:

- `nl_classification`
- `task_planning`
- `route_selection`
- `permission_review`
- `executor_schedule`
- `adapter_execute`
- `audit`

The clipboard example should become:

```text
clipboard NL command -> expected TaskPlan with clipboard.write L2 step
direct clipboard intent -> expected review_required without model involvement
direct clipboard adapter -> expected adapter-specific result
approval step -> blocked only when review_id missing
```

### Adapter Execution Contract

Every adapter should return a typed result:

```json

  "duration_ms": 42,
  "error": null,
  "diagnostics": {
    "command": "wl-copy --type text/plain",

  }

```

Allowed adapter statuses:

- `succeeded`
- `failed`
- `timeout`
- `unavailable`
- `unsupported`
- `cancelled`

Adapter errors must be structured:

- `adapter_timeout`
- `adapter_unavailable`

## Local Acceptance Criteria

### A. Middle-Layer Contract

Pass unit tests proving:

- Legacy single `Intent` commands are normalized into one-step `TaskPlan` objects.
- Executors reject raw utterance strings and unvalidated candidate plans.
- `validate_plan` runs before permission review.
- Invalid schema, unknown capability, invalid target, missing selected route, cyclic dependency, or unknown `expected_state.kind` stops the pipeline before permission review.
- `display.goal`, `display.explanation`, and `display.assumptions` can be changed without changing route selection, permission review, execution order, or adapter payload.
- Every accepted plan has `plan_id`, selected route, step ids, structured provenance, and registered expected states.

### B. Chat vs Task Classification

Pass unit tests for at least these cases:

- `how should VibeOS v0.3 be designed?` -> `chat`
- `open browser` -> `task`
- `explain clipboard permissions and then copy hello to clipboard` -> `mixed`
- `play baby` -> `task`
- `play` -> `clarification`
- `delete downloads` -> `rejected`

### C. Clipboard NL Regression

Pass unit tests proving these all produce a `TaskPlan` with one `clipboard.write` step and non-empty `target.text`:

- `clipboard VibeOS evidence`
- `copy VibeOS evidence`
- `copy to clipboard VibeOS evidence`
- `write VibeOS evidence to clipboard`

### D. Multi-Step Planning

Pass unit tests proving:

- `play baby` emits a multi-step media plan.
- The plan contains ordered dependencies.
- If media capabilities are absent, route selection chooses a browser fallback or returns clarification.
- If required slots are missing, no executable plan is produced.

### E. Route Selection

Pass unit tests proving route scores are deterministic:

- Music route wins when media capabilities are available.
- Browser route wins when media capabilities are unavailable but URI and browser capabilities exist.
- Unknown route is rejected when no route satisfies required capabilities.
- Route result includes `display.explanation` plus structured `score_inputs`.
- Route tie-breaks follow the documented order.
- Route selector cannot add steps, change targets, or create new actions.

### F. Execution Graph

Pass unit tests proving:

- DAG validation rejects cycles.
- A failed dependency marks downstream steps `blocked`.
- Independent read-only steps can be grouped for parallel execution.
- State-changing steps default to sequential execution.
- Execution result preserves root cause by layer.

### G. Permission Integration

Pass unit tests proving:

- Every step receives a permission review.
- L2 steps create review records before execution.
- Approval executes stored plan and step data, not a fresh NL parse.
- Reusing a consumed approval is rejected.
- Audit records include `plan_id`, `step_id`, `action`, `risk_level`, `review_id`, `layer`, and `status`.

### H. Adapter Diagnostics Without VM

Pass unit tests with fake subprocess backends:

- Clipboard adapter reports `written` for a simulated success.
- Clipboard adapter reports `adapter_timeout` for a simulated hanging `wl-copy`.
- The timeout test does not depend on a real `/usr/bin/wl-copy`.
- Direct adapter probe failure does not change NL parser test status.

### I. CLI Contract

Pass local CLI tests:

```powershell
python -m vibeos.cli plan "clipboard VibeOS evidence" --json
python -m vibeos.cli plan "play baby" --json
python -m vibeos.cli ask "clipboard VibeOS evidence" --dry-run --json
python -m vibeos.cli ask "explain clipboard permissions and then copy hello to clipboard" --dry-run --json
```

Expected:

- The first command returns a `TaskPlan` with `clipboard.write`.
- The second command returns selected route, ordered steps, `score_inputs`, and registered `expected_state` objects.
- The third command returns review-required metadata without touching the real clipboard.
- The fourth command returns both chat text and task plan metadata.

## Non-Goals For v0.3

- No requirement for real VM acceptance.
- No requirement to actually automate a music app.
- No requirement for long-term user preference learning.
- No requirement for autonomous background scheduling.
- No requirement for unrestricted shell or D-Bus execution.
- No requirement for full multi-agent orchestration.

## Recommended Definition of Done

v0.3 is complete when:

1. The old single-intent flow still works because it is normalized into one-step `TaskPlan` objects.
2. Raw utterances and unvalidated candidate plans cannot reach permission review or execution.
3. `validate_plan` blocks malformed schema, unknown capabilities, invalid targets, missing selected routes, cycles, and unknown expected states.
4. `display` fields can be edited without changing route selection, permission review, execution order, or adapter payloads.
5. Route selection is deterministic and exposes structured `score_inputs`.
6. `clipboard VibeOS evidence` no longer depends on model luck to become `clipboard.write`.
7. Clipboard adapter timeout is represented as an adapter-layer result, not confused with parser failure.
8. Multi-task and multi-route behavior is explainable in JSON without relying on free-form prose for execution decisions.
9. No acceptance criterion depends on a VM-only environment.
