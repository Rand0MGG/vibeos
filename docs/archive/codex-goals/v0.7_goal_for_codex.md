# VibeOS v0.7 Goal For Codex

Last updated: 2026-06-10

## Overview

This document is the implementation brief for **VibeOS v0.7: personal-agent runtime semantics, layered interaction surfaces, and goal-level recovery**.

v0.6 moved VibeOS from a typed request-to-plan executor toward a session-based runtime control plane.

That was necessary, but it still leaves the system too close to a **bounded capability executor**.

v0.7 must change the product center again.

v0.7 should not be framed as:

- more browser heuristics
- more intent keywords
- more route-specific fallbacks
- more special cases for individual websites or apps

v0.7 should be framed as:

**VibeOS becomes a local personal-agent runtime that can treat the agent as a controlled user proxy, while Linux desktop and browser remain the first concrete execution surfaces.**

This means:

- app cooperation is helpful, but not required
- native APIs are preferred, but not assumed to be sufficient
- accessibility and computer-use style interaction must become first-class architectural concepts
- acceptance must judge whether the user goal was completed, not merely whether a route executed

The design target is closer to a computer-use personal agent than to a capability router, while preserving VibeOS boundaries around permission gates, auditability, and host-owned runtime policy.

## Goal Prompt

Your goal is to implement VibeOS v0.7 on top of the existing v0.6 runtime architecture.

You must not treat this as a greenfield rewrite.

You must preserve and build on the existing host-owned runtime spine:

- typed goal runtime
- typed strategy layer
- typed review and permission policy
- typed audit and run ledger
- typed acceptance and overall outcome reporting

You must not solve v0.7 by:

- adding more browser keyword heuristics
- adding one-off target patches
- restoring a hidden direct-execution path
- bypassing strategy competition
- weakening audit, review, or acceptance semantics

The problem to solve is not "make browser commands pass more often."

The problem is that VibeOS still lacks a strict assistant-facing semantic layer and a strict interaction-surface model above route execution.

v0.7 must add both without breaking the v0.6 runtime contracts that already make the system inspectable.

## Normative Interpretation

This document is normative for v0.7 work.

When implementation tradeoffs arise, Codex should prefer the interpretation that:

- preserves stable user goals over early action collapse
- preserves explicit typed state over convenience shortcuts
- preserves host-owned policy over model-generated execution authority
- preserves structured blocked or incomplete outcomes over misleading success

If a behavior is not explicitly justified by this document, v0.7 should prefer the narrower implementation.

## Terminology Contract

The following terms are not interchangeable in v0.7.

### 1. User goal

The stable user-facing objective.

Examples:

- open Baidu official website
- search WeChat chat history for Alice

The user goal must survive strategy replacement.

### 2. Assistant intent

A typed representation of how the runtime interprets the user goal.

It is higher-level than executable action intent.

It may encode:

- objective kind
- target entity
- completion semantics
- interaction hints

It must not directly encode raw low-level execution steps.

### 3. Strategy

A candidate way to pursue the goal using one or more tool families and one dominant interaction surface.

A strategy is not a route-specific patch and is not identical to a `TaskPlan`.

### 4. Interaction surface

The primary control mode a strategy relies on.

For v0.7, the required conceptual surfaces are:

- `native_action`
- `structured_ui_action`
- `computer_use_action`

### 5. Route

A concrete execution route inside the current registered runtime and domain system.

Routes remain host-owned implementation artifacts under strategy selection.

### 6. Goal completion

A user-goal judgment made after execution, observation, and verification.

It is not equivalent to adapter success, route success, or dispatched commands.

## Product Definition

VibeOS v0.7 should be understood as:

```text
user goal
  -> assistant intent
  -> environment model
  -> strategy candidates across tool families
  -> choose the highest-structure / lowest-fragility path
  -> act
  -> observe
  -> verify
  -> continue / replan / ask user / stop
```

Linux desktop integration remains first-class.

However, desktop actions are no longer the product center.

The product center becomes:

- stable user goal retention
- environment-aware strategy selection
- layered interaction surfaces
- goal-level verification
- inspectable runtime state

## Required Compatibility Boundary

v0.7 must preserve the following public and semi-public contracts unless this document explicitly says otherwise:

- `GoalSpec`
- `TaskPlan`
- `GoalRuntime`
- `StrategyCandidate`
- `EnvironmentProfile`
- `review`
- `audit`
- `run_ledger`
- `execution_status`
- `acceptance_status`
- `overall_status`

Codex may extend these structures.

Codex must not silently remove them, rename them arbitrarily, or replace them with loosely typed dictionaries in the main runtime path.

## Required New Typed Concepts

v0.7 must introduce explicit typed representations for the new semantic center.

At minimum, the implementation should add host-owned typed objects equivalent to:

- `AssistantIntent`
- `AssistantIntentTarget`
- `AssistantCompletionSemantics`
- `InteractionSurface`

Exact class names may vary only if the meaning remains equally explicit and the implementation stays typed and inspectable.

The implementation must not fake this layer by:

- storing everything in one generic `dict[str, object]`
- burying assistant-intent semantics only inside debug output
- inferring interaction surface only from ad-hoc route ids

## Root Cause Statement

The most important current problem is not that one browser flow is wrong.

The real problem is that the system still treats too much of user intent as if it should collapse early into a route-shaped action plan.

That creates several structural failures:

- semantic mistakes are flattened into execution mistakes
- route choice is often made before the runtime has enough strategy space
- browser and app tasks overfit to action tools instead of assistant goals
- the runtime still lacks a first-class notion of interaction depth
- acceptance is still too close to route completion in some flows

v0.7 must solve these structurally.

## Design Principles

### 1. The agent is a controlled user proxy

The runtime should be able to pursue a goal even when the target application has no developer-provided API for that goal.

This does not mean unrestricted desktop automation.

It means the runtime must be able to select among multiple layers of control while remaining policy-governed and inspectable.

### 2. Goal remains stable while interaction mode changes

If a direct structured path fails, the goal should remain stable while the interaction surface changes.

Examples:

- direct URL resolution -> browser search -> page follow-up
- accessibility search -> keyboard shortcut flow -> visual fallback

### 3. Higher-structure control should be preferred

The runtime must prefer the most structured viable control mode:

1. native system action
2. accessibility / structured UI action
3. bounded keyboard and pointer actions
4. visual / OCR-assisted fallback

The runtime must not jump directly to fragile computer-use behavior when a stronger path is available.

### 4. Soft semantics must not be hard-coded into early routing

Hard rules remain appropriate for:

- dangerous requests
- explicit URL forms
- explicit approval boundaries
- capability exposure constraints

Hard rules are not appropriate for prematurely deciding that:

- "official website" always means web search
- "search in app" is unsupported if no app API exists

### 5. Acceptance judges user-goal completion

The runtime must not confuse:

- a dispatched command
- a completed intermediate route
- a completed user goal

Acceptance must explicitly operate at the goal level.

### 6. Recovery policy must classify semantic mismatch

v0.7 must explicitly distinguish:

- observation missing
- tool failure
- environment failure
- semantic mismatch

Semantic mismatch should trigger strategy replacement, not just route retry.

### 7. Safety remains execution-boundary governance

v0.7 must become more capable without becoming casually unsafe.

That means safety should continue to live in:

- review / approval
- allowlists
- tool-family exposure
- typed outcomes
- audit and run ledger

Safety should not depend on making the intent layer artificially stupid.

## New Architectural Center

v0.7 should add a new conceptual center above the current route system.

The center is:

### 1. Assistant intent

This is not identical to low-level executable intent.

It captures:

- what the user is trying to achieve
- what object or target the user refers to
- what kind of completion would count as success
- whether the request implies opening, searching, navigating, or interacting

### 2. Environment model

The runtime must carry explicit environment information into strategy choice.

Important examples:

- visible windows
- focused app
- browser context
- known installed apps
- future accessibility surface availability
- future visual observation availability

### 3. Interaction surface ladder

v0.7 must formalize layered control surfaces:

- `native_action`
- `structured_ui_action`
- `computer_use_action`
- `observer`
- `verifier`
- `resolver`

The current runtime already has some of these families in embryonic form.

v0.7 should make the distinction meaningful for planning and recovery.

It is not acceptable to claim v0.7 completion by editing docs only or by introducing one isolated browser helper.

## v0.7 Scope Decision

v0.7 must remain implementable and locally testable by Codex.

### In scope

- assistant-intent layer above route-level action selection
- strategy selection that can choose among layered interaction surfaces
- goal-level semantic acceptance rules
- explicit `semantic_mismatch` driven strategy replacement
- initial structured control-depth policy
- deterministic local fixtures for app-like interaction surfaces
- browser and app-search vertical slices using fake resolvers / fake observers / fake UI fixtures
- typed, inspectable surface selection evidence
- updated structured runtime payloads and debug traces reflecting assistant intent and interaction surface

### Out of scope

- real OCR as a required local acceptance dependency
- real WeChat support
- real Linux accessibility integration as a required local acceptance dependency
- arbitrary remote computer-use execution
- broad uncontrolled mouse/keyboard automation without policy boundaries
- background omnichannel personal-assistant features
- replacing the host-owned runtime with a model-only planner
- silently broadening dangerous authority such as arbitrary shell or filesystem deletion

## Implementation Constraints

### 1. No hidden authority expansion

v0.7 must not expand authority in order to simulate personal-agent power.

Disallowed examples:

- arbitrary shell execution
- unrestricted file deletion or movement
- unrestricted keyboard and pointer control without policy classification
- hidden bypasses around review-required paths

### 2. No semantic shortcuts disguised as architecture

Disallowed examples:

- special-casing Baidu, WeChat, or one named application as a hard-coded semantic fix
- adding target-specific route rewrites to make tests pass
- encoding assistant intent only as browser-specific conditionals

### 3. No fake "computer use" layer

If v0.7 introduces `computer_use_action` conceptually, the runtime must expose it explicitly in strategy selection, traces, or fixtures.

It is not acceptable to mention computer use in docs but leave the runtime behavior indistinguishable from `native_action`.

### 4. No fake "goal-level acceptance"

It is not acceptable to keep route-level success rules and simply rename them as goal-level acceptance.

The implementation must include testable cases where:

- route execution succeeds
- intermediate verification may succeed
- user-goal acceptance still fails or remains incomplete

## Required Deliverables

### 1. Assistant-intent representation

Add a typed assistant-intent layer that sits above low-level executable action selection.

This layer should capture concepts such as:

- requested objective
- target object or entity
- preferred completion semantics
- interaction hint categories such as direct-open, lookup, in-app-search, follow-up navigation

This layer must not directly emit raw execution steps.

It must remain planner-facing and strategy-facing.

Required properties:

- stable across strategy replacement within one goal
- serializable into structured debug / runtime payloads
- narrow enough to be deterministic in offline tests
- explicit enough that tests can assert its fields directly

### 2. Layered interaction-surface model

Introduce an explicit notion of interaction depth / control mode in the runtime.

At minimum, v0.7 should distinguish:

- native system actions
- structured UI actions
- computer-use style actions

The initial implementation may keep `structured UI` and `computer-use` backed by deterministic fake tools and fixtures rather than real OS integrations.

Required properties:

- the selected interaction surface must be explicit in at least one typed runtime artifact
- the runtime must be able to rank or prefer surfaces
- recovery decisions must be able to respond to surface-specific failure

### 3. Strategy policy for control-depth preference

Add host-owned policy that prefers:

- more structured
- more directly verifiable
- less fragile

paths over weaker ones.

Examples:

- direct site resolution should beat web search when confidence is sufficient
- structured app-search interaction should beat visual fallback when the structured surface is available

Required properties:

- preference policy must be host-owned and deterministic in offline tests
- policy inputs must be inspectable
- policy must not depend on hidden prompt-only reasoning

### 4. Goal-level semantic acceptance

Extend acceptance so that it can represent:

- route completed but goal semantically not completed
- strategy incomplete but goal still viable
- direct success on the intended assistant objective

This should produce strong structured evidence, not prose-only reasoning.

Required properties:

- acceptance evidence must point to the assistant-intent semantics or their equivalent
- acceptance output must distinguish "route succeeded" from "goal completed"
- incomplete semantic outcomes must remain first-class, not downgraded to generic tool failure

### 5. Semantic-mismatch recovery

Upgrade recovery policy so that semantic mismatch becomes a first-class recovery trigger.

Examples:

- "open Baidu official website" must not be considered complete merely because a search page opened
- a direct-open strategy that cannot resolve should preserve the goal and allow a search-followup strategy
- an app-search strategy that fails to locate the target control may fall back to a weaker interaction layer without changing the goal

Required properties:

- semantic mismatch must be visible in the run ledger
- the replacement strategy must remain traceable to the same goal id
- replan decisions must explicitly record do-not-repeat or surface-downgrade logic

### 6. Deterministic app-interaction fixture layer

Add deterministic fake fixtures representing an app-like interaction surface.

The purpose is to let v0.7 prove a user-proxy interaction model without requiring:

- real WeChat
- real Linux accessibility
- real OCR

The fixture layer should model things such as:

- visible controls
- search box availability
- shortcut-driven search mode
- observed result list
- failure to locate controls

Required properties:

- fixtures must be deterministic
- fixtures must not require real GUI dependencies
- fixtures must support both success and semantic-failure cases
- fixture behavior must be asserted by unit or integration tests

### 7. Updated browser semantics

Refactor browser handling so that:

- "official website" is no longer hard-mapped to search as an early semantic decision
- direct-open and search remain candidate strategies
- goal-level acceptance determines whether the chosen strategy actually satisfied the user request

Required properties:

- direct-open vs search choice must be visible in structured strategy artifacts
- early semantic parsing must not hard-map all official-site requests to search
- at least one offline test must prove that a search-page-open result is not automatically accepted as official-site completion

## Minimal Vertical Slices

v0.7 must prove the new architecture with two deterministic local slices.

### Slice A: Goal-level browser opening

Recommended scenario:

```text
user goal: "open Baidu official website"

strategy A:
  resolve site directly
  direct URL open
  observe and verify page identity

strategy B:
  browser search
  observe search result state
  not yet accepted as goal completion unless follow-up navigation evidence is present
```

Required proof:

- the system does not hard-code the request into search at the semantic front door
- route execution alone is insufficient for acceptance
- semantic mismatch can trigger strategy replacement or incomplete outcome

### Slice B: App-local search interaction

Recommended deterministic scenario:

```text
user goal: "search chat history in WeChat for Alice"

strategy A:
  structured UI search tool
  search box found
  query entered
  results observed
  verifier accepts target presence

strategy B:
  shortcut-based fallback
  search mode entered
  query entered
  results observed
  verifier accepts target presence
```

This slice may be implemented entirely with fake app fixtures.

The point is to prove the runtime shape:

- app cooperation is not assumed
- multiple interaction surfaces can pursue the same goal
- verification judges the user objective

## Required Test and Acceptance Matrix

Codex must not treat v0.7 as complete without adding or updating deterministic tests that cover all of the following classes.

### 1. Assistant-intent tests

- parsing or synthesis into assistant-intent form
- stability of assistant intent across strategy replacement
- serialization into runtime/debug payloads

### 2. Surface-selection tests

- native beats weaker surface when sufficient
- structured UI beats computer-use fallback when available
- weaker surface becomes selectable when stronger surface is unavailable

### 3. Goal-level acceptance tests

- route success but goal incomplete
- goal success after follow-up strategy
- semantic mismatch recorded as such rather than generic failure

### 4. Recovery tests

- semantic mismatch triggers strategy replacement
- replacement preserves goal id
- do-not-repeat constraints or equivalent are recorded

### 5. Browser-slice tests

- official-site request is not hard-wired to search
- search-page-open alone is not accepted as final success
- direct-open success is accepted with proper evidence

### 6. App-search fixture tests

- structured UI search success
- fallback strategy success
- failure to locate controls without false success

### 7. CLI / JSON contract tests

Structured outputs for relevant offline or dry-run paths must expose enough information to prove:

- assistant intent or equivalent semantic layer
- selected strategy
- interaction surface
- run attempts
- acceptance and overall outcome

## Required Result Semantics

For v0.7 work, Codex must preserve the rule that the user-facing result should remain interpretable through structured fields first.

That means:

- `overall_status` remains the first-order final judgment
- `execution_status` remains necessary but insufficient
- `acceptance_status` must stay meaningful and not collapse into execution state
- new v0.7 semantic artifacts must be visible without requiring hidden reasoning text

## Migration Discipline

Codex should implement v0.7 in a staged way.

Recommended order:

1. introduce typed assistant-intent concepts
2. expose interaction-surface concepts in strategy artifacts
3. update browser semantics and browser acceptance behavior
4. add deterministic app-interaction fixture slice
5. tighten recovery and test matrix

If implementation must stop mid-way, partial states should still preserve current v0.6 correctness and should not silently degrade supported-task behavior.

## Codex / WSL Acceptance Boundary

v0.7 acceptance must remain inside work Codex can complete in the repository or in WSL.

Codex-owned acceptance may include:

- deterministic local fixtures
- unit and integration tests
- planner and runtime JSON contract checks
- `pytest -q`
- offline CLI checks
- fake observer and fake verifier coverage

Codex-owned acceptance must not require:

- a real Linux accessibility bus
- a real GUI automation session
- a real browser successfully loading public sites
- a real WeChat installation
- live network access

## Disallowed Shortcuts

The following are not acceptable v0.7 solutions:

- adding more route-specific browser keyword heuristics
- treating search-page open as equivalent to official-site open
- implementing "user proxy" only as a slogan without new runtime concepts
- introducing fake semantic recovery that is actually just one-off target fallback
- bypassing review, audit, or typed outcomes to make the tests easier
- silently collapsing structured UI and computer-use layers back into one generic action path
- broadening model authority so that typed runtime structure becomes optional
- shipping only prose explanations of assistant behavior without typed runtime evidence

## Success Criteria

v0.7 is healthy when the repository can demonstrate all of the following locally:

- assistant intent remains stable while strategies change
- browser semantics no longer depend on early hard-coded website-name-to-search mapping
- semantic mismatch is visible in structured runtime state
- acceptance distinguishes route success from goal success
- a deterministic app-search interaction slice passes through the new layered runtime
- audit, run ledger, and debug trace still expose inspectable progress and stop reasons
- offline tests directly assert assistant intent and interaction surface semantics
- no required v0.7 test depends on live network, real WeChat, real OCR, or real Linux accessibility

## Final Design Summary

v0.7 should move VibeOS from:

- a session runtime that still thinks too much in route-shaped desktop actions

to:

- a local personal-agent runtime that treats the agent as a controlled user proxy, prefers structured control surfaces, and judges success at the user-goal level

The system should become more capable without becoming less principled.
