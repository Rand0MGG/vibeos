# VibeOS v0.4 Goal For Codex

Last updated: 2026-06-02

## Purpose

This document is the implementation brief for **VibeOS v0.4: scalable context, domain, and verification architecture**.

It is intentionally limited to work Codex can implement and verify inside the local repository. Fedora VM integration and real desktop validation are out of scope for v0.4 acceptance and will be handled later by the user.

## Goal Prompt

You are working on the `vibeos` repository.

Your goal is to implement VibeOS v0.4 on top of the existing v0.3 typed task pipeline.

Do not replace the v0.3 middle layer. Extend it.

The problem to solve is not "add random capabilities". The problem is that the current agent cannot scale cleanly:

- it needs relevant system state without exposing all state
- it needs higher-level domain abstractions
- it needs at least one real domain-shaped vertical slice for meaningful tests
- it must not rely on a monolithic prompt containing every domain, route, and state field
- it must remain inspectable, testable, and maintainable

The risk to avoid is building a large framework before one narrow domain works. v0.4 should prove the architecture with a browser vertical slice, then use media only to prove domain routing and fallback.

The v0.4 design target is:

```text
utterance
  -> v0.3 utterance analysis
  -> domain router
  -> observation request
  -> context package resolver
  -> capability exposure manifest
  -> candidate plans from active domains only
  -> route selection
  -> validation
  -> review
  -> execution
  -> postcondition verification
  -> run trace and audit
```

## Proven Patterns To Follow

v0.4 follows mature agent and assistant design patterns:

- Hermes-style agents organize tools into toolsets, load skills on demand, restrict MCP tools by allowlist, and isolate subagent context instead of exposing everything globally.
- Claude Code-style agent workflows separate planning, tool permission, tool execution, and traceable results.
- Automotive voice assistants such as Xiaoai route user input into narrow skill domains such as navigation, calls, and media before filling slots and invoking structured endpoints.

For VibeOS, the equivalent is:

- activate only relevant domains
- expose only relevant routes and context packages
- keep execution and policy code-enforced
- make domain capabilities semantic but still bounded
- verify postconditions instead of only checking that a command was emitted

These patterns are guidance, not product claims. v0.4 must stay model-provider agnostic and must not depend on external LLM calls, network access, VM state, or a real desktop session for local acceptance.

Important broker boundary: local acceptance must explicitly use `RuleIntentBroker` or a fake broker. It is not enough to rely on a remote broker failing and falling back locally. A machine with `OPENAI_API_KEY`, `DEEPSEEK_API_KEY`, `OPENAI_MODEL`, or similar environment variables must still run the same deterministic local acceptance path.

## v0.4 Scope Decision

v0.4 should add some real usefulness, but keep scope controlled.

### Full vertical slice: browser

Browser is the v0.4 domain to complete end-to-end.

Implement:

- domain routing
- context package selection
- browser route templates
- browser semantic capabilities
- browser policy matrix
- execution through current lower-level primitives where possible
- fake/local verifier harness
- structured postcondition verification
- CLI and broker visibility

The browser vertical slice may use injectable fake/local adapters in tests. Real browser launch is useful as a later manual check, but it is not a v0.4 completion gate.

Initial browser semantic capabilities:

- `browser.open_url`
- `browser.search_web`
- `browser.open_site_search`

### Partial vertical slice: media

Media should become first-class for routing and route competition, but v0.4 should not require true playback automation.

Implement:

- media domain registration
- media context package
- media route templates
- planner-visible `media.search`, `media.play`, and `media.pause`
- explicit browser fallback when dedicated media execution is unavailable
- verifier registration and fake/local verifier tests

Do not make real MPRIS playback, web playback, account-dependent music apps, or browser media autoplay a v0.4 completion gate.

Media fallback must not be fake by omission. The plan path must first consider a media-domain route, record why dedicated media execution is unavailable, and then select a declared browser fallback route.

### MCP

Do not implement MCP in the first v0.4 cut unless all core deliverables are complete.

If MCP-related code is introduced, it must be limited to a small host-owned registry boundary and must not replace `TaskPlan`, validation, review, execution graph, verification, or audit.

## Required Deliverables

Implement the following local architecture pieces.

### 1. DomainPack

Add a compact domain package abstraction.

A `DomainPack` should contain:

- `domain_id`
- domain label
- route definitions
- allowed context package IDs
- capability families
- policy defaults
- default verifier IDs
- optional fallback domain IDs

This gives future domains a repeatable structure. Adding a new domain should not require rewriting the core planner.

Required packs:

- `browser`
- `media`

### 2. DomainRegistry

Add a host-owned registry for available domains.

The registry must:

- load domain packs
- validate domain definitions
- expose active domain definitions to the router and planner
- reject unknown domain IDs
- reject routes that reference unknown capabilities, context packages, or verifiers

This registry must be used by routing and planning. It must not be dead documentation.

### 3. ContextPackageRegistry

Add a host-owned registry defining the only system-state packages the planner may consume.

Required packages:

- `session_context`
- `window_context`
- `browser_context`
- `media_context`

Each package must define:

- `package_id`
- typed schema
- producer function
- `ContextBudget`
- redaction policy
- freshness / TTL metadata

Do not expose arbitrary raw system state. The planner must receive only named, bounded context packages.

Producer functions must be host-owned and mockable. They may return an unavailable or stale package status, but they must not cause planner tests to depend on a live OS session, browser process, media player, or network.

### 4. ContextBudget

Add a budget contract for every context package.

Each context package should define:

- `max_items`
- `max_bytes`
- `ttl_ms`
- `redaction_policy`
- `sensitive_fields`

Acceptance must prove that oversized or unknown context payloads cannot enter planning unbounded.

### 5. ObservationRequest

Add a typed request connecting domain routing to context loading.

It must contain:

- active domain IDs
- requested context package IDs
- optional postcondition package IDs

Validation rules:

- requested package IDs must exist in `ContextPackageRegistry`
- requested packages must be allowed by active domains
- postcondition package IDs must also be registered and allowed
- duplicate package IDs must be normalized or rejected deterministically
- unknown package IDs must fail before planning, not become empty packages

### 6. ObservationReceipt

Add a typed receipt recording what was actually loaded.

It should include:

- requested package IDs
- loaded package IDs
- skipped package IDs
- payload byte sizes
- freshness timestamps
- redaction/truncation flags
- validation errors or warnings

This makes context debugging concrete. If planning goes wrong, tests and logs can show exactly what context was made visible.

### 7. CapabilityExposure

Add a per-turn capability exposure manifest.

The planner-facing manifest should include only what the planner may use:

- active domain IDs
- exposed route IDs
- exposed capability IDs
- exposed context package IDs

It must not include hidden route definitions, hidden capability definitions, or global tool lists.

Trace-only metadata may include:

- hidden domain IDs
- hidden route IDs
- hidden counts

The planner should receive this narrowed manifest, not the global route universe.

Acceptance must prove a browser-only request does not see media-only routes or media-only context by default.

### 8. Domain Router

Add a router stage after v0.3 utterance analysis.

Important boundary:

- The router consumes `UtteranceAnalysis`.
- The router does not replace the v0.3 classifier.
- The router does not emit executable actions.
- The router does not create a `TaskPlan`.

Its job is only to determine:

- candidate domains
- active fallback domains
- whether clarification is needed before deeper planning
- observation request

Ambiguity rule:

- If domain confidence is low and no safe default exists, return clarification instead of activating many domains.
- If multiple domains are plausible, activate only the minimal set needed for route competition.
- Fallback domains must come from `DomainPack.optional_fallback_domain_ids`; the router must not invent fallback domains per turn.

The router must narrow planner inputs so planning sees only:

- active domain definitions
- active domain routes
- resolved context package payloads
- current capability exposure

### 9. Domain-Scoped Routes

Refactor or extend routes so they are domain-scoped and machine-readable.

At minimum:

- browser routes are separate from media routes
- media requests compete inside the media domain first
- browser fallback is explicit and testable
- route definitions include default verifiers
- route definitions include required capabilities and preconditions

The route selector may score already-formed routes, but it must not invent a new route.

### 10. Browser Domain Adapter Surface

Introduce first-class browser semantic capabilities:

- `browser.open_url`
- `browser.search_web`
- `browser.open_site_search`

Implementation may internally reuse lower-level primitives such as `portal.open_uri`, but the domain-facing plan and policy layer must expose browser-level semantics.

Browser route examples:

- `browser_open_url_route`
- `browser_search_web_route`
- `browser_site_search_route`

### 11. Browser PolicyMatrix

Add a policy matrix for browser semantic capabilities.

Recommended policy:

- `browser.search_web` with a normal query: L1
- `browser.open_url` with normal `https://` target and no credentials: L1
- `browser.open_url` with embedded credentials: L3
- `browser.open_url` with `file://`, `javascript:`, `data:`, or unknown scheme: L3
- `portal.open_uri` remains a generic primitive with stricter policy

Do not globally downgrade `portal.open_uri` from L2 to L1.

Privacy rule: user-provided query text may be searched when policy allows it, but context-derived sensitive fields must never be inserted into a browser query or URL unless an explicit typed step and review path authorizes it.

### 12. Media Domain Adapter Surface

Introduce planner-visible media semantic capabilities:

- `media.search`
- `media.play`
- `media.pause`

If dedicated media execution is unavailable locally, the architecture must still support:

- domain routing
- route competition
- validation
- browser fallback
- verifier registration
- clear unavailable execution status

### 13. Postcondition Verification

Add typed postcondition verification.

Required verifier infrastructure:

- verifier registry
- verifier result model
- verifier execution hook after adapter execution
- verifier outputs included in plan execution result
- verifier outputs included in audit-friendly payloads
- verifier input observation separated from adapter status

Initial verifier IDs:

- `browser_url_opened`
- `browser_search_route_completed`
- `media_playback_state_available`

Verifier failures must be distinguishable from adapter failures.

Verification must not degenerate into "adapter returned succeeded". A verifier may use fake/local observations in tests, but it must evaluate a typed postcondition against a typed observation and must have at least one negative test where adapter execution succeeds but verification fails.

### 14. VerifierHarness

Add a fake/local verifier harness.

v0.4 local acceptance must not depend on a real browser, real GNOME session, or real media player. Tests should be able to inject fake context packages and fake verifier observations.

The harness should support both success and failure observations. It is not enough to assert that a verifier was called.

### 15. ScenarioFixture

Add reusable scenario fixtures for regression tests.

Each fixture should include:

- utterance
- locale or language tag when relevant
- expected utterance analysis
- active domains
- observation request
- context package payloads
- expected exposed routes
- expected selected route
- expected validation result
- expected verification result

This is more durable than one-off tests because it keeps router, context, planner, route, and verifier expectations aligned.

Fixtures should assert typed fields and stable IDs. They should not assert exact free-form explanation text except where the explanation field itself is the feature under test.

### 16. RunTrace

Add a structured per-turn trace.

It should include:

- utterance analysis
- domain routing
- observation request
- observation receipt
- capability exposure
- selected route
- validation
- review
- execution
- verification

`vibe plan --json` and `vibe ask --json` should expose enough trace metadata to debug which layer caused a failure.

### 17. Offline Broker Boundary

Add an explicit local/offline broker boundary for acceptance.

Required behavior:

- unit tests must inject `RuleIntentBroker` or a fake broker instead of relying on the default broker
- CLI acceptance paths must provide a deterministic offline mode, such as `--offline` or an equivalent test-only broker override
- offline mode must prevent remote model requests even when API key and model environment variables are present
- remote broker failure followed by local fallback must not count as a passing local acceptance case
- any remote-model integration test must be opt-in and skipped by default

The goal is reproducibility. Two machines with different environment variables must produce the same v0.4 local acceptance result.

## Hard Constraints

### Architecture constraints

1. Execution, policy, validation, canonicalization, verification, and audit must remain code-enforced, not prompt-enforced.
2. The model or planner must not see all current state by default.
3. The model or planner must not invent arbitrary state queries.
4. New state exposure must happen only through named context packages.
5. New domain capability abstractions must sit above low-level primitives and below arbitrary GUI automation.
6. Browser should be the only full v0.4 vertical slice.
7. Media should support routing and fallback but should not require real playback.
8. The implementation must preserve repo simplicity. Do not introduce a framework-like directory explosion.
9. Do not introduce decorator-heavy plugin magic. Registries should be plain data plus explicit validation.
10. Local acceptance must be deterministic without remote model calls.
11. Tests and local acceptance commands must force a local or fake broker instead of depending on environment-variable absence.
12. Remote broker fallback behavior is a runtime feature, not a local acceptance mechanism.

### Prompt-surface constraints

1. Do not implement v0.4 by expanding one giant planner prompt.
2. Do not load all domain definitions into every plan request.
3. Do not load all route definitions into every plan request.
4. Do not load all context package payloads into every plan request.
5. Do not expose global MCP or external tool universes to the planner.

### Compatibility constraints

1. Preserve existing v0.3 review and audit behavior for already-supported flows.
2. Preserve existing runtime transport behavior unless a change is necessary and well-tested.
3. Preserve current structured result style for `vibe plan --json` and `vibe ask --json`, extending it rather than replacing it blindly.
4. Legacy one-step task flows must remain accepted through the v0.3 `TaskPlan` path.
5. If an offline CLI flag or broker override is added, it must not break the existing default runtime path.

## Recommended File Layout

Prefer a minimal extension of the current structure.

Recommended new modules:

```text
src/vibeos/domain_models.py
src/vibeos/domain_registry.py
src/vibeos/domain_router.py
src/vibeos/observation.py
src/vibeos/verifiers.py
src/vibeos/run_trace.py
```

Recommended placement:

- Put `DomainPack`, `ContextBudget`, `ObservationRequest`, `ObservationReceipt`, `CapabilityExposure`, verifier result, fixture, and trace dataclasses in `domain_models.py`.
- Put `DomainRegistry` and `ContextPackageRegistry` in `domain_registry.py`. Put `VerifierRegistry` in `verifiers.py`.
- Put browser and media pack definitions in `domain_registry.py` first. Split into `src/vibeos/domains/browser.py` and `src/vibeos/domains/media.py` only after the definitions become too large.
- Keep browser policy matrix as plain data near the browser pack or existing permission/capability code. Do not create a large policy subsystem for three browser capabilities.

Optional only after core v0.4 is stable:

```text
src/vibeos/mcp_registry.py
```

Continue to use and extend:

```text
src/vibeos/task_models.py
src/vibeos/planner.py
src/vibeos/routes.py
src/vibeos/task_validation.py
src/vibeos/execution_graph.py
src/vibeos/broker.py
src/vibeos/runtime.py
src/vibeos/reviews.py
```

## Minimum Implementation Order

Implement in this order unless repository constraints force a better sequence:

1. typed models for domains, domain packs, context budgets, observation requests, observation receipts, planner-facing capability exposure, verifier results, scenario fixtures, and run traces
2. domain registry, context package registry, and verifier registry with explicit validation
3. browser domain pack, browser routes, browser semantic capabilities, and browser policy matrix
4. domain router consuming v0.3 `UtteranceAnalysis`
5. observation resolver and capability exposure manifest for browser-only requests
6. planner narrowing to active browser domain, active browser routes, active context, and exposed browser capabilities only
7. browser verifier harness and browser postcondition verification
8. offline broker boundary for tests and CLI acceptance
9. CLI and broker integration for the browser vertical slice
10. media domain pack, media routes, media context, media route competition, and explicit browser fallback
11. local acceptance tests and updated design/status docs

Do not count v0.4 as healthy if only trace output changed. The planner input itself must be narrowed before candidate generation or route selection.

Do not implement MCP in the first pass unless the above items are already complete.

## Acceptance Criteria

All acceptance must be achievable by Codex locally. Do not use VM-only criteria as completion gates.

### A. Typed architecture

Codex must add typed, tested local structures for:

- domain packs
- domain registry entries
- context package registry entries
- context budgets
- observation requests
- observation receipts
- capability exposure manifests
- verifier results
- scenario fixtures
- run traces

Acceptance:

- local tests prove invalid domain, context, verifier, or route definitions are rejected
- local tests prove invalid observation requests are rejected
- local tests prove context budgets cap payload size and item count
- local tests prove run traces contain all expected layer keys
- local tests prove all new JSON-facing structures carry schema/version fields where needed

### B. Planner input narrowing

The router and planner boundary must prove inactive domains and inactive routes are not globally injected into the planning path.

Acceptance:

- a browser-only request does not receive media-only context packages by default
- a browser-only request does not expose media-only routes by default
- a planner-facing capability exposure manifest does not contain hidden route definitions
- a media request activates media plus explicit browser fallback domains only
- planner-visible route sets are narrowed to active domains
- trace metadata records hidden domains or hidden counts without leaking them into planner input

### C. Context package discipline

Context exposure must be bounded and explicit.

Acceptance:

- planner-facing context is composed only from registered packages
- package schemas are enforced
- unknown package IDs cannot enter planning
- oversized context payloads are truncated or rejected according to `ContextBudget`
- observation receipt records loaded, skipped, truncated, and redacted packages
- unavailable or stale package states are represented explicitly and do not crash planning
- tests use injected producers rather than live OS state

### D. Browser full vertical slice

Browser must become the first fully wired semantic domain.

Acceptance:

- `vibe plan "open https://example.com" --json` produces browser-domain semantics rather than only generic primitive semantics
- `vibe plan "打开 https://example.com" --json` produces the same browser-domain semantics
- `vibe plan "search web for hello" --json` produces a browser search route
- `vibe plan "搜索 hello" --json` produces a browser search route
- `vibe ask "open https://example.com" --dry-run --json` exposes browser domain, observation, narrowed routes, policy, verifier metadata, and trace
- local tests cover browser route selection and validation
- local tests cover browser policy matrix for safe HTTPS, embedded credentials, local file URLs, and unsupported schemes
- local tests cover at least one non-dry-run browser-domain flow through fake/local adapter and verifier harness

### E. Media partial vertical slice

Media must become a first-class routing and planning domain even if dedicated execution remains unavailable.

Acceptance:

- `vibe plan "play baby" --json` shows media-domain analysis and route competition
- `vibe plan "我想听 baby" --json` shows media-domain analysis and route competition
- local tests prove media requests do not bypass domain routing
- local tests prove browser fallback is explicit when dedicated media execution is unavailable
- local tests prove unavailable dedicated media execution is recorded before browser fallback is selected
- local tests prove media context package schema is enforced
- local tests prove media verifier registration exists
- no v0.4 acceptance depends on real media playback

### F. Verification

Postcondition verification must exist as typed infrastructure.

Acceptance:

- local tests prove verifier registration works
- local tests prove execution results can carry structured verifier outputs
- local tests prove verifier failures are distinguishable from adapter failures
- local tests prove adapter success plus verifier failure is represented as a verification-layer failure
- local tests prove browser verifier outputs appear in run trace and audit-friendly payloads

### G. Broker and CLI integration

The new architecture must be wired through the local user-facing path.

Acceptance:

- local tests cover `vibe plan --json` returning domain, observation request, observation receipt, capability exposure, narrowed planning, and verifier metadata
- local tests cover `vibe ask --dry-run --json` exposing the same plan-path structures
- local tests cover browser-domain review and execution metadata without relying on real browser launch
- local tests cover trace output for both successful and failed layer outcomes

### H. Offline broker determinism

Local acceptance must not change based on whether the developer machine has remote model credentials.

Acceptance:

- unit tests for NLU, planner, router, CLI, and broker paths inject `RuleIntentBroker` or a fake broker
- CLI acceptance has a deterministic offline path for `vibe plan --json` and `vibe ask --dry-run --json`
- tests set fake `OPENAI_API_KEY`, `DEEPSEEK_API_KEY`, and model environment variables and still prove no remote broker call is attempted
- tests prove remote broker failure plus fallback is reported as remote-broker behavior, not counted as local acceptance success
- default runtime remote-broker behavior may remain available outside offline acceptance, but it must be opt-out or overrideable for tests

### I. Backward stability

The new work must not destroy already-working v0.3 flows.

Acceptance:

- all existing tests continue to pass after required updates
- new tests cover the added v0.4 behavior
- full local test suite passes

### J. Documentation

The repository must contain updated local architecture documentation matching the implemented code.

Acceptance:

- update docs describing:
  - domain packs
  - domain registry
  - context package registry
  - context budgets
  - observation request and receipt
  - capability exposure
  - browser/media domain surfaces
  - policy matrix
  - verifier model
  - scenario fixtures
  - run trace
- documentation must describe local acceptance only; VM verification remains a separate later step

## Completion Standard

You may consider this goal complete only when all of the following are true:

1. the local architecture pieces above are implemented in code
2. the planner path is narrowed by domain, context package, route, and capability exposure
3. browser is a first-class full vertical planning/execution/verification domain
4. media is a first-class routing/planning domain with explicit browser fallback
5. typed postcondition verification exists
6. run traces expose router, observation, context, planning, route, validation, review, execution, and verification layers
7. local CLI and broker paths expose the new structures
8. local acceptance is deterministic with remote broker credentials present
9. full local tests pass
10. repository docs are consistent with the implementation

Do not claim completion based on VM behavior. VM validation is intentionally deferred to the user.
