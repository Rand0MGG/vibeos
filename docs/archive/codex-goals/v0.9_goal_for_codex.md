# VibeOS v0.9 Codex 目标文档

最后更新：2026-06-24

## 1. 文档目的

本文档定义 **VibeOS v0.9** 作为下一阶段 Codex 的实现目标。

v0.9 不再把重点放在“补更多 capability”或“补更多特判规则”，而是聚焦于把当前已经成型的 v0.8 语义运行时，继续推进为一个更成熟、可恢复、可暂停、可审计、可维护的 **桌面 Agent 控制循环**。

本文档同时承担三种职责：

1. 说明当前代码已经做到什么、还缺什么。
2. 规定 v0.9 的目标架构与实现边界。
3. 给出可执行、可验证的验收标准，尤其是 WSL 下的开发与测试流程。

---

## 2. 当前代码基线

截至当前仓库状态，VibeOS 已经具备以下基础：

- `CapabilityBroker` 已经承载主入口、规划、审查、执行、验收、审计与 trace 汇总。
- `planner.py` 已具备：
  - primary understanding artifact
  - goal synthesis
  - candidate set generation
  - bounded candidate selection
  - named website 的 goal-directed candidate augmentation
- `broker.py` 已具备：
  - `_run_task_plan_loop()`
  - per-step safety review record
  - structured attempts / replanning / acceptance wiring
  - named website 语义路径，如 `browser_named_direct_open_route` 与 `browser_search_followup_route`
- `acceptance.py` 与 `semantic_acceptance.py` 已具备：
  - `execution_status`
  - `acceptance_status`
  - `overall_status`
  - semantic summary / semantic decision
- `failure_classifier.py` 与 `replanner.py` 已具备基础失败分类与证据驱动重规划。
- `task_trace.py` / `audit.py` / `run_ledger.py` 已具备结构化追踪骨架。
- 当前 WSL 全量测试基线已跑通：
  - `pytest -q`
  - 结果：`317 passed`

但是，当前代码仍然存在几个明确短板：

1. `CapabilityBroker` 仍然过重，接近 God Object。
2. `_run_task_plan_loop()` 仍然是 broker 内部的一段大循环，而不是独立、可复用、可恢复的 Goal Loop 模块。
3. `AgentRuntime` 仍然以整段 strategy 执行为主，没有成为 step-level loop 的一等执行底座。
4. pause / resume / review snapshot 还没有形成真正的长任务恢复能力。
5. observation 仍然不够“每步前后强制化、分层化、可升级化”。

### 2.1 Prerequisite Gate

v0.9 是建立在 v0.8 已经稳定完成之上的控制循环升级，不是补完 v0.8 的替代版本。

Codex 开始 v0.9 主体实现前，必须先确认并保住以下基线：

- v0.8 typed runtime、semantic planning、centralized step safety review、semantic acceptance、trace / audit 骨架已经在当前仓库可用。
- v0.8 的 named website slice 已经能用 fake provider / fixture 路径完成本地确定性验收。
- semantic decision 与公开 `execution_status` / `acceptance_status` / `overall_status` 的映射已经稳定，模型不能直接拥有公开 runtime status。
- step safety review 仍然是唯一能产出 `allow / deny / review_required` 的执行边界。
- 本地测试可以显式注入 fake understanding / route selection / semantic acceptance / observation provider，而不是依赖 live LLM、真实网络、真实浏览器或真实桌面。
- v0.8 的核心回归测试和 WSL 基线在开始 v0.9 前重新测量并记录。

如果这些条件不成立，Codex 应先修复 v0.8 基线，而不是把缺失能力塞进 v0.9 的 GoalLoop 重构里。

v0.9 可以在同一实现过程中修复少量直接阻塞 GoalLoop 接入的下层缺陷，但这些修复必须作为前置修复明确记录，不能被包装成 v0.9 新能力。

## 3. v0.9 的产品目标

v0.9 的目标不是推倒重写，而是：

**在保留当前 v0.8 typed runtime、semantic planning、centralized step safety review、acceptance 与 tracing 骨架的前提下，把主执行路径升级为真正的 step-level、observation-centered、suspendable、recoverable Goal Loop。**

用一句话概括：

```text
v0.8 更像“模型参与的结构化任务运行时”
v0.9 要把它推进成“真正可循环控制电脑任务的受控 Agent Runtime”
```

---

## 4. v0.9 核心原则

v0.9 必须同时满足以下原则：

### 4.1 小步执行

- 默认一轮只执行一个 step。
- 只有明确原子的小 batch 才允许在一个 loop tick 内执行多个紧耦合低风险 step。
- 不允许回到“选中 strategy 后一口气执行完整 strategy”的主路径。

### 4.2 观察是 loop 核心，不是附属品

- 每轮至少包含：
  - `observe_pre`
  - `act`
  - `observe_post`
  - `verify`
- observation 必须成为 loop 的一级输入，而不是仅供最终 acceptance 使用。

### 4.3 语义交给模型，边界交给宿主

- 自然语言理解、任务重解释、语义重规划、模糊验收必须允许模型参与。
- capability 暴露、step safety、schema validation、audit ownership 仍然由宿主控制。

### 4.4 不打补丁式修问题

- 遇到问题优先修结构，而不是继续堆 route-specific branch。
- 不允许把 v0.9 做成“在 broker 里继续堆更多 if/else 和 fallback”。

### 4.5 能暂停、能恢复、能追责

- review-required、needs-user-input、外部状态变化都必须可暂停。
- 恢复时必须从 loop snapshot 恢复，而不是重跑整段任务。
- 每一轮 observe / act / verify / repair / replan 都必须可追踪。

### 4.6 优先采用成熟方法，不发明新体系

v0.9 不应通过引入新的 agent DSL、临时状态词汇或高度隐式的黑箱控制器来实现。

Codex 必须优先采用成熟、常见、已被大量工程系统验证的方法：

- 显式 typed 状态机，而不是隐式 if/else 漫游
- reducer 风格的状态转移，与副作用执行解耦
- append-only trace / audit 事件流，而不是事后拼接日志
- checkpoint / snapshot 恢复，而不是失败后整段重跑
- fake provider / fixture 驱动的本地验收，而不是依赖 live model、真实网络或真实桌面偶然成功
- feature flag 渐进切换，而不是一次性替换全部主路径

v0.9 应优先复用当前仓库已经存在的稳定骨架，而不是重新发明同类概念：

- `CandidateSet`
- `SemanticDecision`
- `ReviewStore`
- `TaskTraceStore`
- `RunLedger`
- `overall_status` / `execution_status` / `acceptance_status`

明确禁止：

- 为 GoalLoop 再发明一套新的用户可见状态系统
- 为 repair / replan 发明自由格式脚本语言
- 为 suspend / resume 发明脱离现有 review store / trace / audit 的并行持久化通道
- 用“模型更聪明”代替结构约束

## 5. v0.9 非目标

以下内容不是 v0.9 的完成前提：

- 增加更多真实桌面 capability
- 在 VM 中完成全面真实桌面自动化
- 引入无限制的 computer-use 风格自由执行
- 让模型直接获得 shell 或未注册 authority
- 用真实公网依赖作为本地开发验收前提

v0.9 的目标是 **控制循环升级**，不是 capability 扩张。

## 6. 目标架构

v0.9 目标结构应当演进为：

```text
CapabilityBroker
  ├─ request ingress
  ├─ trace session bootstrap
  ├─ planning bootstrap
  ├─ strategy/candidate assembly
  ├─ GoalLoop invocation
  ├─ audit finalization
  └─ CommandResult formatting

GoalLoop
  ├─ observe_pre
  ├─ choose_next_action
  ├─ step_review
  ├─ execute_step
  ├─ observe_post
  ├─ verify_step_progress
  ├─ classify_failure
  ├─ repair / retry / replan
  ├─ suspend / resume
  └─ finish / stop / block

AgentRuntime
  ├─ session / goal / turn / ledger ownership
  ├─ step execution primitive
  └─ strategy-level compatibility path
```

推荐采用的成熟实现形态之一：

```text
LoopState (typed snapshot)
  +
LoopReducer (pure-ish state transition)
  +
LoopRunner / Effect Ports (review, runtime, observation, trace, audit)
```

也就是说：

- `LoopState` 负责表达可恢复状态
- `LoopReducer` 负责根据当前阶段、观测、执行结果、失败分类产生下一步决策
- `LoopRunner` 负责调用 observation / review / runtime / persistence 等有副作用的端口

Codex 不必拘泥于这几个名字，也不需要为了形式强行实现完全函数式 reducer 架构。

真正的硬要求是强分层、弱耦合：

- 状态表达、状态推进、副作用执行、持久化、审计必须能被清楚区分。
- reducer-style 逻辑应优先保持可测试、可解释、低副作用，但允许采用更符合当前代码结构的等价实现。
- 只要能证明职责边界清晰、测试覆盖充分、没有重新形成 God Object，就不要求机械套用某一种架构模式。

如果把状态推进、外部调用、日志持久化重新揉回一个 God Object，这就不算完成 v0.9。

### 6.1 允许保留的兼容层

v0.9 允许保留：

- 现有 `AgentRuntime.continue_goal()` 作为兼容路径
- 现有 `CapabilityBroker` 的旧接口形态
- 现有 `TaskPlan` / `PlanAttempt` / `RunLedger` 数据骨架

但 v0.9 的新主路径应当逐步切换到独立 `GoalLoop`。

## 8. 对现有代码的强制改造要求

### 8.1 `CapabilityBroker` 必须降责

v0.9 完成时，`CapabilityBroker` 不应继续承担完整 loop 逻辑。

最低要求：

- broker 不再直接持有主 loop 的细粒度状态转移逻辑。
- broker 不再同时负责：
  - planning loop
  - step execution orchestration
  - resume state machine
  - repair policy decision

允许 broker 保留：

- 入口
- planning bootstrap
- goal loop 初始化
- 最终结果封装

### 8.2 `AgentRuntime` 必须新增 step execution primitive

v0.9 必须新增一个明确的 step-level 执行 API。

建议形态：

```python
execute_strategy_step(...)
```

要求：

- 单步执行
- 返回 typed `StepRunResult` 或等价结构
- 更新 state
- 可被 `GoalLoop` 调用

`_execute_strategy()` 可以保留为兼容层，但不能继续作为 v0.9 主路径核心。

### 8.3 `_run_task_plan_loop()` 必须外提或被替代

当前 broker 中的 `_run_task_plan_loop()` 说明系统已经有“loop 的雏形”，但 v0.9 不应继续把它保留为 broker 私有膨胀逻辑。

完成标准：

- 主执行循环迁移到独立模块。
- broker 中仅保留调用入口与结果桥接。

### 8.4 step-level review 必须支持上下文重审

v0.9 不仅要保留 plan-level review，还必须支持：

- step 执行前重新审查
- 基于最新 observation 的 contextual re-review

必须覆盖的场景：

- 当前窗口已变化
- 当前页面已变化
- 当前目标对象已变化
- 原本低风险动作在新上下文下变为高风险

### 8.4.1 必须继承 v0.8 的安全优先级

v0.9 不得因为 loop 重构而回退 v0.8 已经明确的安全边界。

必须继续成立的规则：

- step safety review 仍然是唯一有权产出 `allow / deny / review_required` 的执行边界
- 普通 `search` / `type query` / `in-app lookup` 的 default allow 必须让位于敏感数据规则
- 如果某一步虽然形式上像搜索，但预期会暴露聊天记录、私信历史、邮件内容、财务记录、健康信息、凭据或其他敏感数据，则必须落到 `review_required` 或更严格
- 如果进入搜索模式与暴露敏感内容在该应用里不可分，则进入搜索本身就必须重审

这条是对 v0.8 的继承，不是可选优化。

### 8.5 review / user input 必须支持 resume

不允许停在：

- `needs_review`
- `needs_user_input`

之后只能“重新执行整段任务”。

必须实现：

- 保存 loop snapshot
- 批准后恢复
- 用户补充信息后恢复
- 恢复时避免重复执行已完成 step

### 8.6 observation 必须分层

至少需要在结构上区分：

- `L0`：cheap observation
- `L1`：targeted observation
- `L2`：expensive observation

v0.9 不要求必须上 OCR 或视觉模型，但必须为 observation escalation 留出 typed 接口，而不是把所有观察都挤进同一层 producer。

### 8.7 引入 `same_action_no_progress`

v0.9 必须把“动作执行成功但没有推进目标”作为一等失败类型。

要求：

- failure taxonomy 中存在该类或语义等价类
- 能基于前后 observation 比较判断 progress
- 能阻止 loop 无意义重复

## 9. 目标 Loop 状态机

v0.9 推荐状态机：

```text
BOOTSTRAP_UNDERSTANDING
  ↓
INIT_LOOP
  ↓
OBSERVE_PRE
  ↓
PLAN_OR_SELECT_STEP
  ↓
STEP_REVIEW
  ↓
ACT
  ↓
OBSERVE_POST
  ↓
VERIFY
  ↓
DECIDE
    ├─ COMPLETE
    ├─ RETRY
    ├─ REPAIR
    ├─ REPLAN
    ├─ NEEDS_REVIEW
    ├─ NEEDS_USER_INPUT
    ├─ BLOCKED
    └─ BUDGET_EXHAUSTED
```

要求：

- 这是运行时状态机，不是纯文档概念。
- trace 中必须能看出每轮处于哪个阶段。
- `BOOTSTRAP_UNDERSTANDING` 只允许作为 loop 启动前或 loop 启动时的 bootstrap 阶段，不是每个 tick 的常规阶段。
- 常规 tick 必须复用 `primary_understanding_id`，不得每轮重新理解用户意图。
- 如果后续 observation 或用户输入确实改变了语义基础，必须通过显式 `UnderstandingRefinement` 或 `UnderstandingSupersession` 进入语义重解释，而不是静默重跑 understanding。

### 9.1 Loop 内部状态不是新的公开契约

上面的状态机是 GoalLoop 的内部运行阶段与控制决策，不是新的用户可见运行时状态系统。

v0.9 必须继续沿用当前公开契约：

- `execution_status`
- `acceptance_status`
- `overall_status`

Loop 内部阶段、semantic acceptance、公开运行时状态三者必须显式分层。

v0.9 必须继续保留 v0.8 已经建立的 semantic acceptance 边界：

```text
GoalLoop execution facts + observations + verifier facts
  -> SemanticEvidenceSummary
  -> SemanticDecision
  -> SemanticAcceptanceDecision
  -> existing acceptance / result status mapping
```

GoalLoop 不得因为自己处于 `COMPLETE`、`REPLAN`、`BLOCKED` 等内部决策状态，就直接生成公开 `acceptance_status` 或 `overall_status`。

对于语义完成、语义未完成、语义失败这三类结果，GoalLoop 必须先产出或消费既有 `SemanticAcceptanceDecision`，再由现有 acceptance 层映射到公开状态。

最低映射要求：

| Loop 决策或事实 | Public execution_status | Public acceptance_status | Public overall_status |
| --- | --- | --- | --- |
| pending review before execution | `not_started` | `skipped` | `needs_review` |
| pending user clarification before execution | `not_started` | `skipped` | `needs_user_input` |
| step execution failed at adapter/transport/runtime layer | `failed` | `skipped` | `failed` |
| `SemanticDecision=complete` from `SemanticAcceptanceDecision` | `succeeded` | `passed` | `completed` |
| `SemanticDecision=incomplete` from `SemanticAcceptanceDecision` | `succeeded` | `indeterminate` | `incomplete` |
| `SemanticDecision=semantic_failure` from `SemanticAcceptanceDecision` | `succeeded` | `failed` | `incomplete` |
| capability, route, or required execution surface is unavailable before a runnable step exists | `not_started` | `skipped` | `blocked` |
| internal runtime construction error or invariant violation prevents a valid loop result | `failed` | `skipped` | `failed` |
| dry-run path | `dry_run` | `skipped` | `dry_run` |

实现要求：

1. Codex 不得把 `COMPLETE`、`REPLAN`、`BUDGET_EXHAUSTED` 之类 loop 决策直接暴露成新的 `overall_status`。
2. `needs_review` 只能来自 review/safety 边界，不是模型语义结论。
3. `BUDGET_EXHAUSTED` 必须通过现有失败/阻塞契约落地，不能单独扩展新的公开状态，除非同一改动明确修改 `task_models.py` 并同步所有 CLI、audit、tests。
4. capability / route / surface 不可用必须优先映射为 `blocked`；只有内部错误、适配器错误或状态机不变量破坏才映射为 `failed`。
5. 当结果依赖语义完成判断时，必须存在可追踪的 `semantic_acceptance_decision_id` 或等价引用。
6. 测试必须能证明 GoalLoop 没有绕过 `semantic_acceptance.py` 直接把语义结果写成公开状态。

## 10. 失败与修复策略要求

v0.9 的 failure handling 不应只停留在“换一个 route 再试”。

至少应支持以下失败语义：

- `target_not_found`
- `app_not_installed`
- `window_not_found`
- `permission_denied`
- `review_required`
- `network_unavailable`
- `browser_navigation_failed`
- `page_load_timeout`
- `semantic_mismatch`
- `acceptance_unverified`
- `acceptance_failed`
- `same_action_no_progress`
- `state_changed_externally`

每种失败至少要支持以下决策之一：

- `retry`
- `repair`
- `replan`
- `ask_user`
- `request_review`
- `stop`

要求：

- repair 优先于全量 replan
- replan 必须消费最新 observation、failure history、已完成 step
- 不允许简单重新跑 `plan_turn(utterance)` 然后丢失上下文

### 10.1 Loop termination reasons 不是 failure taxonomy

以下属于控制层终止原因，不属于 failure classifier 输出的 failure class：

- `budget_exhausted`
- `max_retry_exceeded`
- `max_step_exceeded`
- `policy_stop`

实现要求：

- failure classifier 负责解释外部事实、执行结果和语义不匹配。
- loop policy 负责预算、步数、重试次数和终止条件。
- public status mapping 必须消费 loop termination reason，但不能把它混入 semantic failure taxonomy。
- `budget_exhausted` 可以导致 `blocked` 或 `failed`，但必须通过 loop policy 与现有公开状态映射落地，而不是作为普通 failure class 参与 repair/replan 分类。

### 10.2 Repair / Replan 必须重新进入 bounded candidate boundary

v0.9 的 repair / replan 不能成为绕过 v0.8 candidate boundary 的新后门。

必须继续成立：

- 如果 repair 只是在同一个已注册 step 内调整参数，它必须保留原 step / candidate 的来源引用，并通过 step validation 与 step safety review。
- 如果 repair 或 replan 需要产生新的 executable step，它必须重新产出或消费 `CandidateSet`，并且新 step 只能来自注册 capability 与受限候选集。
- 模型可以参与 repair / recovery / replan 的语义选择，但只能在 host-owned candidate set 内选择、排序、拒绝、请求澄清或停止。
- GoalLoop 不得接受模型临时提出的 free-form executable step。
- replan trace 必须记录 consumed observation ids、failure history ids、completed step ids、candidate_set_id，以及 selected route / strategy decision id。

必须新增或扩展测试证明：

- replan 返回未知 `candidate_id` 会被确定性拒绝。
- acceptance failure 触发 replan 时会生成或消费新的 bounded `CandidateSet`。
- repair 不能创建未注册 capability step。
- 已完成 step 不会因为 replan 被隐式重跑。

## 11. 模型参与边界

v0.9 继续沿用 v0.8 的核心原则：

### 模型必须参与的地方

- task understanding
- clarification generation
- 语义重规划
- 模糊验收
- 需要自然语言理解的 repair / recovery 选择

### 模型不应直接拥有的地方

- capability 发明权
- route outside candidate set
- review bypass
- public runtime status ownership
- shell / root / hidden authority

### v0.9 新增要求

loop-level decision 中如果涉及：

- 用户目标语义是否已经变化
- 当前失败是否说明计划已经过期
- 当前 observation 是否意味着需要 ask user

则必须允许模型参与，而不是完全靠 rule chain 决定。

但模型参与不是每轮 tick 的默认动作。

只有同时满足以下条件时，GoalLoop 才应升级到模型参与：

- deterministic evidence 不足以安全、准确地做出下一步决策。
- 当前问题包含真实语义歧义、目标重解释、语义验收或需要自然语言解释的 recovery 选择。
- 低成本 deterministic rule、schema validation、candidate validation、policy check 无法充分解决该问题。
- 本次模型调用会消费已有 structured artifacts，而不是重新读取整段原始对话并重做 understanding。

默认情况下，以下事项不应调用模型：

- budget / retry / step count 判断
- capability registry lookup
- schema validation
- candidate id 合法性校验
- public status mapping
- review store persistence

测试必须能证明普通无歧义 tick 不会调用模型，而语义歧义或 evidence 不足时会通过 fake provider 触发模型参与。

### 11.1 本地验收必须使用 fake providers，而不是 live provider

为了让 v0.9 成为 Codex 可稳定执行的目标，本地 loop 验收必须显式使用 deterministic fake providers 或 fixture providers。

本地测试与 WSL 验收中，以下依赖不能作为通过前提：

- 真实 LLM 成功返回
- 实时网络可用
- 真实浏览器状态偶然正确
- 真实桌面环境刚好满足预期

允许使用的成熟做法：

- fake understanding provider
- fake clarification provider
- fake route / strategy selection provider
- fake semantic acceptance provider
- fake observation provider
- fake approval / user-input events
- app/browser fixtures

`vibe ask --offline --dry-run` 这类 CLI 检查只能作为 smoke check，不能替代 GoalLoop 的本地确定性验收。

注意：fake approval / user-input events 不能替代 Slice B 对真实 `ReviewStore` 持久化、批准、恢复、消费路径的验收。

## 12. Logging / Trace / Audit 要求

v0.9 的 loop 改造不能只存在于内存。

必须落到结构化日志中。

### 12.1 Trace

trace 至少要记录：

- `loop_started`
- `observe_pre_completed`
- `step_selected`
- `step_review_completed`
- `step_executed`
- `observe_post_completed`
- `step_verified`
- `failure_classified`
- `repair_decided`
- `replan_decided`
- `loop_suspended`
- `loop_resumed`
- `loop_completed`

### 12.2 Audit

最终 audit 至少可关联到：

- `trace_run_id`
- `understanding_id`
- `candidate_set_id`
- `selected_route_decision_id`
- `semantic_acceptance_decision_id`
- `loop_snapshot_id` 或等价 resume 关联标识

### 12.3 Review persistence

review store 必须能持久化：

- pending step
- pending reason
- snapshot
- approval 后恢复所需最小状态

### 12.4 Loop snapshot 最小字段

v0.9 的 suspend / resume 不能只保存一段 prose 或一个 review id。

可恢复 snapshot 至少必须包含以下结构化字段或语义等价字段：

- `loop_snapshot_id`
- `trace_run_id`
- `goal_id`
- `primary_understanding_id`
- `candidate_set_id`
- `selected_route_decision_id` 或当前 route / strategy 引用
- `current_step_id`
- `completed_step_ids`
- `pending_review_id` 或 `pending_user_input_id`
- `pre_observation_id` 与最近一次 `post_observation_id`
- `attempt_history` 或可关联到 `RunLedger` 的 attempt ids
- `failure_history`
- `model_artifact_ids`，用于关联 understanding、route decision、semantic summary、semantic acceptance

恢复时必须从这些字段重建 loop 的下一步，而不是重新跑整段 `plan_turn(utterance)` 或重新执行已完成 step。

## 13. v0.9 最小必做垂直切片

v0.9 不要求覆盖所有 domain。

但必须至少把以下切片做成真正的 loop 级别能力：

### Slice A：命名网站打开

示例：

- `帮我打开百度官网`
- `open Baidu official website`

要求：

- step-level execution
- direct open / search follow-up 可重规划切换
- search page 不算最终完成
- page identity 作为 semantic acceptance 依据
- 支持 `same_action_no_progress` 检测

### Slice B：需要审批的中断与恢复

本切片必须使用确定的本地 fixture，不允许实现时临时挑选一个“刚好能触发 review”的动作。

推荐 fixture：

- 构造一个已注册 capability 的 fake step，安全层稳定返回 `review_required`。
- 该 step 不触达真实网络、真实桌面、真实剪贴板或真实外部应用。
- approve 事件可以来自本地测试 fixture，但 review 的创建、持久化、批准、恢复、消费必须经过真实 `ReviewStore` / `reviews.py` 路径。
- `ReviewStore` 可以使用测试临时目录或临时 `reviews.jsonl`，但不能在 Slice B 验收中被完全 mock 掉。

如果仓库已有更合适的 review fixture，可以使用等价 fixture，但必须在测试名或测试数据中固定下来。

除 synthetic fake step 之外，v0.9 还应补一个已有真实 capability path 的 suspend / resume 覆盖。

这个测试可以使用 dry-run、offline、fake adapter 或本地 fixture，仍然不得依赖真实网络、真实桌面副作用、真实剪贴板或真实外部应用。

它要证明 review / resume 不只在 synthetic step 上成立，也能接入现有 capability -> plan/step -> review -> GoalLoop -> ReviewStore -> resume 的真实接线路径。

必须证明：

- loop 遇到 review-required 时暂停
- review store 保存 snapshot
- pending review 被写入真实 review persistence 介质
- approve 更新同一条 pending review 记录
- resume 从 review store 重新读取 snapshot，而不是继续使用内存对象
- approve 后从 pending step 恢复
- 已完成 step 不重复执行

### Slice C：需要用户补充信息的中断与恢复

示例：

- `open that site we discussed yesterday`

要求：

- clarification 不是终态失败
- loop 进入 `needs_user_input`
- 保存 snapshot
- 输入补充目标后恢复

## 14. 实现阶段建议

在进入任何结构改造前，Codex 应先补“first failing tests”，再逐步实现。

推荐顺序不是为了好看，而是为了减少回归面并复用成熟 TDD / strangler-fig 迁移方法。

### 阶段 0：first failing tests 与 feature flag

完成标准：

- 先新增最小 GoalLoop 测试壳，不直接改主路径
- 引入显式 feature flag，使新旧路径可切换
- 明确兼容路径默认仍走旧主路径，避免一次性切换

建议优先补的 first failing tests：

- `test_goal_loop_executes_one_step_at_a_time`
- `test_goal_loop_suspends_for_review`
- `test_review_approval_resumes_from_pending_step`
- `test_goal_loop_suspends_for_user_input`
- `test_same_action_no_progress_is_classified`
- `test_loop_decision_maps_back_to_public_runtime_statuses`
- `test_sensitive_search_review_overrides_default_allow`

### 阶段 1：抽出 GoalLoop 骨架

完成标准：

- 新增 `loop_models.py`
- 新增 `goal_loop.py`
- broker 调用独立 loop，而不是内嵌大段循环
- 先抽 reducer / state / runner 边界，再迁移更多行为

### 阶段 2：单步执行能力

完成标准：

- `AgentRuntime` 新增 step execution primitive
- loop 可逐步执行 strategy steps
- 兼容旧 strategy path

### 阶段 3：pre/post observation 与 step verify

完成标准：

- 每步前后 observation
- step verify 独立
- trace 可见

### 阶段 4：review / user input suspend-resume

完成标准：

- snapshot 持久化
- resume 能跑通

### 阶段 5：evidence-driven repair / replan

完成标准：

- rule-based repair 先落地
- model-guided replan 接入
- `same_action_no_progress` 可触发 stop 或 replan

## 18. v0.9 成功标准

只有当以下条件全部成立时，v0.9 才能算完成：

1. v0.8 prerequisite gate 被重新测量并记录，未通过时先修复 v0.8 基线。
2. 项目存在独立、typed、可测试的 Goal Loop 模块。
3. 主路径支持 step-level execute / observe / verify / repair / replan。
4. review-required 与 needs-user-input 都支持 snapshot-based suspend / resume。
5. `AgentRuntime` 提供 step-level 执行 primitive。
6. failure taxonomy 至少覆盖 `same_action_no_progress` 并被真实测试覆盖。
7. named website slice 能在新 loop 中完整跑通。
8. 语义完成、语义未完成、语义失败必须继续通过 `SemanticAcceptanceDecision` 和现有 acceptance 映射产生公开状态。
9. review slice 使用确定 fixture，能证明真实 ReviewStore 持久化、approve 后从 pending step 恢复且不重复执行已完成 step。
10. repair / replan 必须重新进入 bounded candidate boundary，不能创建未注册 executable step。
11. user-input slice 能证明补充信息后从 snapshot 恢复。
12. WSL 全量 `pytest -q` 通过。
13. WSL 结构化 CLI 检查通过。
14. loop 行为在 trace / audit / review store 中可追踪。
15. loop snapshot 包含最小结构化字段，且恢复不依赖重跑整段任务。
16. 整个实现没有把 v0.9 变成新的 God Object。

## 19. 总结

v0.9 的核心不是“让模型更自由”，而是：

**让当前已经具备模型理解、结构化规划、集中安全审查、语义验收能力的 VibeOS，升级为一个真正按 step 推进、按 observation 决策、能暂停、能恢复、能重规划的受控电脑 Agent Runtime。**

对 Codex 来说，v0.9 的正确实现顺序是：

1. 先把 loop 独立出来。
2. 再把执行粒度降到 step。
3. 再补 suspend / resume。
4. 再把 repair / replan 变成 evidence-driven。
5. 始终用 WSL 全量回归守住当前基线。

这份文档就是后续 Codex 工作的目标定义与验收标准。
