# VibeOS v0.8 Goal For Codex

Last updated: 2026-06-13

## Overview

This document is the implementation brief for **VibeOS v0.8: model-centered task understanding, constrained model-guided planning, centralized execution-boundary safety, and semantic acceptance**.

v0.7 moved VibeOS toward a typed personal-agent runtime with:

- stable goal concepts
- layered interaction surfaces
- explicit recovery
- goal-level acceptance

That is necessary, but it still leaves too much system behavior trapped in deterministic rules that were originally added to compensate for weak understanding.

v0.8 must change the center again.

v0.8 should not be framed as:

- more keyword heuristics
- more early task-type shortcuts
- more route-specific patches
- more duplicated safety checks at multiple layers
- more repeated model parses of the same user request

v0.8 should be framed as:

**VibeOS becomes a model-centered local personal-agent runtime in which natural-language understanding, planning, replanning, and semantic completion judgment are model-guided, while authority, capability exposure, normalization, and execution safety remain host-owned.**

This means:

- natural-language interpretation should be model-led
- route and strategy choice should be model-guided inside host-owned boundaries
- semantic recovery should be model-guided rather than rule-scripted
- semantic acceptance should use both rules and model judgment
- safety should be centralized at the execution boundary rather than spread across lexical front doors
- token usage should be controlled by architecture, not by weakening understanding quality

## Goal Prompt

Your goal is to implement VibeOS v0.8 on top of the existing v0.7 runtime architecture.

You must not treat this as a greenfield rewrite.

You must preserve and build on the host-owned runtime spine:

- typed runtime artifacts
- typed review and permission policy
- typed audit and run ledger
- typed capability registry
- typed strategy and acceptance structures
- explicit `execution_status`, `acceptance_status`, and `overall_status`

You must not solve v0.8 by:

- adding more deterministic keyword routing
- adding more target-specific branches
- letting models emit arbitrary executable authority
- scattering safety decisions across intent parsing, planning, and execution
- trading away reliability just to reduce token consumption

The problem to solve is not "use the model more often."

The problem is that VibeOS still uses rules in several places where the real work is semantic:

- task understanding
- route intent selection
- strategy selection among valid options
- semantic replanning after failure
- semantic completion judgment from observations
- clarification of ambiguous user goals

v0.8 must move those responsibilities into constrained model-guided modules while keeping authority host-owned.

## Prerequisite Gate

v0.8 must not be treated as an excuse to finish unfinished lower-layer work.

Codex should only count v0.8 implementation as on-track when the following prerequisite baseline is already stable in the repository:

- v0.6 runtime spine is present and locally healthy
- durable run ledger and typed runtime artifacts are already usable
- v0.7 browser / user-proxy semantic slice is already locally healthy
- goal continuity, strategy replacement, and semantic non-completion already have deterministic local test coverage

If these prerequisites are not true, the correct action is to repair the lower layer first rather than smuggle foundation work into v0.8 under a model-centered label.

v0.8 is therefore an architectural refinement layer above an already working typed runtime, not a substitute for finishing v0.6 or v0.7.

## Normative Interpretation

This document is normative for v0.8 work.

When implementation tradeoffs arise, Codex should prefer the interpretation that:

- uses models for semantic decisions
- keeps rules only where host-owned hard boundaries are necessary
- centralizes safety review at the executable step boundary
- reuses prior model artifacts instead of re-parsing the same request repeatedly
- spends tokens where they improve correctness, not where rules can already guarantee correctness

If a behavior is not explicitly justified by this document, v0.8 should prefer the narrower host-owned authority surface and the stronger semantic layer.

## Root Cause Statement

The central v0.8 problem is not only that rules are sometimes inaccurate.

The deeper problem is that **semantic responsibility is currently split across too many rule layers**.

That causes predictable failure patterns:

- correct model understanding can be lost because later rule stages do not consume it properly
- repeated parsing of the same utterance can let a later bad model response overwrite an earlier good one
- route planning is often limited by deterministic builders that expect explicit surface forms
- semantic recovery is constrained by brittle failure-to-route mappings
- acceptance is still too close to verifier mechanics rather than goal completion semantics
- safety policy is harder to reason about because it is partially mixed into early understanding

v0.8 must solve these structurally.

## Product Definition

VibeOS v0.8 should be understood as:

```text
user utterance
  -> model-led task understanding
  -> host-owned normalization and schema validation
  -> model-guided route / strategy planning inside registered capability space
  -> host-owned per-step safety review
  -> execute approved steps
  -> collect structured observations and verifier facts
  -> model-guided evidence summary
  -> rule + model semantic acceptance
  -> continue / replan / ask user / stop
```

The product center becomes:

- model-led semantic understanding
- host-owned authority boundaries
- centralized execution safety
- structured evidence reuse
- semantic completion judgment

## Architectural Thesis

v0.8 should adopt the following system thesis:

### 1. Natural-language work should be model-led

If a stage requires understanding user language, latent intent, ambiguity, target semantics, or semantic equivalence, the system should use a model.

### 2. Authority remains host-owned

Models may choose among allowed semantic options, but they must not create new capabilities, new hidden tools, or new authority outside registered policy.

### 3. Safety belongs at the executable boundary

Safety review should happen when a structured executable step is about to run.

Safety should not be implemented as scattered lexical filters in the understanding layer.

### 4. The system should parse once, then reuse

One user request should produce one primary structured understanding artifact.

Later stages should consume and refine that artifact rather than casually reparsing the original utterance.

### 5. Token efficiency is an architectural concern

The system should reduce wasted model usage by:

- reusing structured artifacts
- separating cheap from expensive model calls
- avoiding repeated full-context prompts
- only escalating when uncertainty or semantic ambiguity justifies it

Token savings are good only when they do not materially reduce correctness.

## What Must Become Model-Guided

The following areas must gain explicit model participation in v0.8.

### 1. Task understanding

Task understanding should become model-led.

This includes:

- task vs chat vs clarification vs unsupported interpretation
- target disambiguation
- implicit objective inference
- named website understanding
- named application intent
- cross-language phrasing
- multi-clause user requests

Rules may still validate structure, but rules should not be the main source of semantic understanding.

Required ownership rule:

- each user turn must produce exactly one primary understanding artifact unless an explicit supersession event occurs
- later model stages must consume that artifact rather than silently replacing it

Disallowed behavior:

- reparsing the raw utterance and overwriting the earlier valid understanding without an explicit refinement or supersession record

### 2. Goal and subgoal synthesis

Goal synthesis should become model-guided.

This includes:

- stable user-goal representation
- subgoal decomposition
- completion semantics
- interaction hints
- semantic assumptions and uncertainty markers

The current deterministic goal synthesis layer is not sufficient as the long-term center.

Required stability rule:

- goal and subgoal synthesis must reference the primary understanding artifact by id
- if later semantic evidence changes the interpretation, the runtime must emit an explicit refinement or supersession artifact rather than mutating the earlier artifact in place

### 3. Route planning

Route planning should become model-guided inside host-owned route and capability registries.

This means the model may decide:

- which registered domain best matches the goal
- which registered route family should be preferred
- which strategy should be attempted first

This does not mean the model may invent arbitrary unregistered execution paths.

Required boundary:

- host-owned deterministic layers must generate the candidate route and strategy set first
- the model may only rank, select, reject, defer, or request clarification among those candidates
- the model must not fabricate a new executable candidate outside the registered candidate set

### 4. Strategy selection and downgrade choice

When multiple valid strategies exist, semantic choice among them should involve a model.

Examples:

- direct-open vs search-follow-up for a named website
- structured UI interaction vs shortcut fallback
- native route vs browser-mediated route

The allowed strategy space remains host-owned.

The model chooses among allowed candidates and may recommend downgrade order.

Required output discipline:

- model outputs at this stage should identify existing candidate ids
- if no candidate is acceptable, the model must return a structured non-selection outcome such as `clarify`, `unsupported`, or `blocked`
- the model must not output free-form instructions that implicitly define a new hidden strategy

### 5. Replanning

Replanning after failure should become model-guided.

The replanner should consume:

- structured failure classification
- structured step diagnostics
- observation packages
- prior attempts
- preserved task understanding

The model should decide:

- whether the goal is still viable
- whether a different route or surface should be tried
- whether the target interpretation should be refined
- whether clarification is preferable to more retries

Replanning must remain bounded by registered route and capability space.

### 6. Clarification generation

Clarification questions should become model-guided.

The model should ask for the smallest missing piece of information needed to continue safely and correctly.

### 7. Semantic evidence summary

Before final acceptance, the system should use a model to summarize structured observations into a semantic state judgment.

Examples:

- whether the current page appears to match the intended official site
- whether a search result state satisfies the user's requested target
- whether app-search results appear to match the requested person or conversation

This summary must be based on structured observations and verifier evidence, not on unconstrained free-form hallucinated state.

Required input discipline:

- semantic evidence summary must reference structured observation, verifier, and execution artifact ids
- it must not operate on raw prose alone when structured evidence exists

### 8. Semantic acceptance

Final completion judgment should use both rules and model reasoning.

Rules should continue to determine:

- whether execution happened
- whether safety review passed
- whether hard verifier failures occurred
- whether hard environment failures occurred

The model should determine:

- whether the resulting state semantically satisfies the user goal
- whether the evidence is sufficient
- whether the task should be marked complete, incomplete, or semantically failed

Required traceability rule:

- semantic acceptance must reference the primary understanding artifact, the semantic evidence summary artifact, and the hard deterministic acceptance facts it consumed

Required ownership rule:

- the model-guided semantic layer must not emit public runtime status fields directly
- it may emit only an internal semantic decision enum plus evidence rationale
- public `execution_status`, `acceptance_status`, and `overall_status` remain runtime-owned outputs

## Semantic Decision Vocabulary And Public Status Mapping

v0.8 must not introduce a second user-visible status system.

The implementation should keep two layers explicitly separate:

- internal semantic decision vocabulary
- public runtime status contract

The internal semantic decision vocabulary should be limited to:

- `complete`
- `incomplete`
- `semantic_failure`
- `clarification_needed`

The model should emit only this internal semantic decision vocabulary, not public runtime statuses such as:

- `completed`
- `failed`
- `blocked`
- `needs_review`
- `needs_user_input`

`needs_review` is a safety/runtime outcome, not a semantic model verdict.

The public runtime contract must remain aligned with the existing code surface in [src/vibeos/task_models.py](/E:/codex_project/vibeos/src/vibeos/task_models.py:13) and [src/vibeos/broker.py](/E:/codex_project/vibeos/src/vibeos/broker.py:2731).

The current public contract is:

- `execution_status`: `not_started | dry_run | succeeded | failed`
- `acceptance_status`: `passed | failed | indeterminate | skipped`
- `overall_status`: `failed | needs_review | dry_run | completed | incomplete | blocked | needs_user_input`

Mandatory mapping table:

| Runtime situation | Internal semantic decision | Public execution_status | Public acceptance_status | Public overall_status |
| --- | --- | --- | --- | --- |
| safety review unresolved or approval missing before execution | no semantic success allowed | `not_started` | `skipped` | `needs_review` |
| clarification is required before execution | `clarification_needed` | `not_started` | `skipped` | `needs_user_input` |
| capability missing, route impossible, or host blocks execution before a runnable step | `semantic_failure` or no-selection outcome | `not_started` | `skipped` | `blocked` or `failed`, chosen by existing runtime policy |
| execution fails at transport, adapter, or environment layer | no semantic success allowed | `failed` | `skipped` | `failed` |
| execution succeeds and semantic evidence proves goal satisfaction | `complete` | `succeeded` | `passed` | `completed` |
| execution succeeds but evidence is partial, weak, or still unresolved | `incomplete` | `succeeded` | `indeterminate` | `incomplete` |
| execution succeeds but semantic evidence shows the wrong page, wrong target, or wrong outcome | `semantic_failure` | `succeeded` | `failed` | `incomplete` |
| dry-run preview path | semantic decision optional and non-terminal | `dry_run` | `skipped` | `dry_run` |

Implementation rules:

1. The model must never emit `overall_status` directly.
2. `needs_review` must be produced only by the step safety layer or approval workflow.
3. `completed` is public runtime output; `complete` is the internal semantic verdict that may justify it.
4. `semantic_failure` must not become a new public `overall_status`; it maps through existing acceptance/runtime fields.
5. If Codex adds new internal semantic labels in the future, it must also extend this mapping table in the same change.

## Acceptance Conflict Precedence Table

v0.8 must define a fixed precedence order for acceptance conflicts.

The purpose of this table is to prevent different modules from resolving rule/model disagreement in inconsistent ways.

The acceptance pipeline must follow this order:

### Level 1: hard blocking facts override all model optimism

The following conditions are authoritative and must not be overruled by any model-guided semantic judgment:

- `safety deny`
- unresolved `review_required`
- execution did not occur
- hard environment failure
- hard verifier failure

If any Level 1 condition is present, the runtime must not return internal semantic success and must not expose `overall_status=completed`.

Allowed outcomes in this case include:

- `blocked`
- `failed`
- `needs_review`
- `incomplete`

but not `completed`.

### Level 2: rule-owned execution facts remain authoritative

The following facts remain host-owned and deterministic:

- whether a step executed
- whether execution timed out
- whether the transport failed
- whether an adapter reported failure
- whether a verifier produced a hard failure
- whether a required safety approval was missing

The model may interpret the semantic meaning of these facts, but it must not rewrite them.

Disallowed examples:

- treating `execution_status=failed` as if execution succeeded
- treating a hard verifier failure as if verification passed
- treating a denied step as if it had been approved

### Level 3: model judgment applies only after hard blockers are cleared

Only when no Level 1 blocker is present may the model decide among semantic outcomes such as:

- `complete`
- `incomplete`
- `semantic_failure`
- `clarification_needed`

This is the level where the model may judge questions such as:

- whether the opened page is actually the intended official site
- whether an app-local search result appears to match the requested target
- whether the available evidence is sufficient to conclude completion

### Level 4: route success is not goal success

Even when:

- execution succeeded
- no hard verifier failure exists
- the route behaved as designed

the runtime must still allow semantic non-completion.

Examples:

- a search page opened, but the user asked for the official website itself
- an app entered search mode, but no matching result was observed
- an intermediate route completed, but the user-goal postcondition was not satisfied

In these cases, the model may return `incomplete` or `semantic_failure`, and the runtime may continue or replan.

### Level 5: model judgment cannot create success from missing evidence

If the evidence is weak, partial, stale, or contradictory, the model must not upgrade the internal semantic decision to `complete` or the public runtime result to `overall_status=completed`.

Allowed outcomes include:

- `incomplete`
- `clarification_needed`
- `semantic_failure`

The runtime should prefer these over false success.

## Acceptance Conflict Rules

The following implementation rules are mandatory for v0.8:

1. A model-guided semantic conclusion must be derived from structured evidence, not from raw free-form intuition.
2. A hard verifier failure must override model optimism.
3. A safety denial must override all semantic judgments.
4. Missing approval must block execution regardless of semantic plausibility.
5. Route-level success must not be automatically promoted to goal completion.
6. If evidence does not justify completion, the runtime must prefer internal `incomplete`, which maps to public `acceptance_status=indeterminate` and `overall_status=incomplete`, over false completion.

## Required Acceptance Tests

Codex must not treat v0.8 as complete without deterministic tests that prove the precedence table above.

At minimum, tests should cover:

- hard verifier failure plus optimistic semantic model output still results in non-success
- safety denial plus optimistic semantic model output still results in non-success
- route success plus semantic non-completion results in `incomplete` or equivalent non-success outcome
- weak or partial evidence does not get upgraded to `completed`
- semantic completion is allowed only when no hard blocker exists and evidence is sufficient

## What Should Remain Rule-Based

v0.8 should drastically reduce rules, but not remove them where they are genuinely required.

The following must remain host-owned deterministic layers.

### 1. Capability registry

The set of allowed capabilities, tool families, and execution surfaces remains rule-based and explicit.

### 2. Schema validation

Intent, plan, review, execution, and acceptance payloads must be structurally validated by deterministic code.

### 3. Target normalization

Canonicalization of fields such as:

- `content -> text`
- `url/name -> uri`
- `app -> name`

should remain deterministic.

### 4. Plan and step validation

Rules should continue to validate:

- registered capability references
- route integrity
- target field legality
- dependency-graph consistency
- expected-state schema correctness

### 5. Execution-boundary safety review

Every executable step must pass through one centralized host-owned safety layer immediately before execution.

This layer should return one of:

- `allow`
- `deny`
- `review_required`

### 6. Adapter facts

Raw execution outcomes such as:

- timeout
- unavailable
- adapter success
- verifier unavailable
- transport failure

should remain deterministic host-owned facts.

### 7. Audit and ledger persistence

Storage of structured runtime artifacts must remain host-owned.

## Explicit Safety Position

v0.8 should remove lexical safety gating from the understanding front door.

Examples of what should not happen:

- rejecting a request simply because the text contains "delete"
- rejecting a request simply because the text contains "install"
- using keyword presence as a substitute for structured policy review

Instead, safety should be unified at the executable step boundary.

Lexical or semantic front-door analysis may still emit a structured `risk_hint`, but that hint is advisory only.

It may influence:

- logging
- trace visibility
- later safety review context
- whether clarification should be preferred

It must not by itself directly decide:

- `allow`
- `deny`
- `review_required`

The correct order is:

1. understand the user request
2. synthesize a goal
3. build candidate plans
4. select a plan or strategy
5. before each executable step, send the normalized step to the safety layer
6. execute only approved steps

This improves:

- semantic accuracy
- policy consistency
- auditability
- false-positive avoidance

## Safety Posture For v0.8

v0.8 should materially relax the current safety posture for ordinary user-like interaction.

The goal is:

- do not make the system timid by default
- do not require review for most benign observation and navigation actions
- continue to block or escalate actions with destructive, privilege-bearing, external, or privacy-sensitive consequences

This means v0.8 should prefer:

- broad default allowance for read, navigation, lookup, focus, and bounded search actions
- explicit review or denial only where the action meaningfully increases user risk

## Default Safety Classification Policy

Unless a stronger host-owned policy overrides it, v0.8 should move toward the following default classification shape.

### 1. Default allow

The following classes should normally be allowed without manual review when the capability is registered and the step is structurally valid:

- read-only observation
- opening an app
- opening a URL
- browsing navigation
- website lookup
- focusing a window
- listing windows or apps
- entering an in-app search mode only when the app context is not privacy-sensitive
- typing a bounded search query only when the app context is not privacy-sensitive and the query is not expected to reveal sensitive records
- switching tabs, panes, or views
- scrolling
- other bounded user-like navigation actions that do not create external side effects or persistent mutation

This is the main safety relaxation intended for v0.8.

Override rule:

- these default-allow examples are shape-based heuristics only
- they must yield immediately to the sensitive-data and external-side-effect rules below
- the implementation must not classify a step as `allow` merely because it lexically resembles `search`, `type query`, or another bounded navigation pattern

### 2. Review required

The following classes should normally require review unless a stricter or more specific host-owned policy applies:

- sending or publishing data to external recipients
- submitting forms with user-visible consequences
- cross-application write actions
- reading or exporting clearly sensitive personal content
- reading or extracting private message history, credentials, financial data, secrets, or equivalent high-sensitivity content
- large-scope computer-use actions with broad or unclear side effects
- actions that confirm dialogs, authorizations, purchases, or account changes
- actions whose target scope is ambiguous but potentially sensitive

### Sensitive app-local search boundary

v0.8 must treat privacy-sensitive app-local search more strictly than ordinary website lookup or generic navigation.

Examples of privacy-sensitive contexts include:

- private messaging
- email
- financial applications
- health data applications
- password or secret stores
- enterprise chat or document systems containing private records

Rules:

1. Opening or focusing a sensitive app may still be `allow`.
2. Once the next step is expected to reveal message history, participant names, record contents, or other private data, the step must default to `review_required`.
3. If entering search mode and revealing sensitive content are operationally inseparable in that app, the transition into search must itself be treated as `review_required`.
4. The implementation must not classify sensitive chat-history search as harmless bounded navigation merely because the step text looks like "search" or "type query".

### 3. Deny

The following classes should normally remain denied unless future product versions explicitly broaden authority:

- destructive deletion
- overwrite or destructive move operations
- arbitrary shell execution
- privilege escalation
- software installation
- hidden persistence or background injection
- unregistered capabilities
- capability use outside registered host-owned boundaries

v0.8 should not weaken these deny classes.

## Sensitive Data And External Side-Effect Rule

v0.8 must not collapse all non-destructive actions into `allow`.

Even when an action is not destructive, it should still require review or denial when it involves:

- external communication
- sensitive personal data
- account state changes
- authorization or confirmation
- privilege-bearing execution

This requirement exists because many dangerous actions are not destructive in the narrow sense of file deletion.

Examples:

- sending a message
- copying private chat content into another app
- reading a conversation transcript in bulk
- authorizing a login or payment
- installing software

None of these should become automatically allowed merely because they are not deletions.

Precedence requirement:

- this rule overrides the default-allow bucket above
- if a nominally bounded search, typed query, or in-app lookup is expected to reveal sensitive content, the step must be treated as `review_required` or stricter
- the classifier must reason about target data sensitivity and likely revealed content, not only superficial action shape

## One-Parse-Then-Reuse Requirement

v0.8 must explicitly prevent the repeated-reparse failure mode.

The implementation should follow this rule:

- one user turn gets one primary understanding artifact
- later stages reuse that artifact
- later model calls should consume structured prior artifacts, not restart from the raw utterance unless explicitly necessary

This requirement exists because repeated reparsing can:

- waste tokens
- increase inconsistency
- let a later malformed model output overwrite an earlier correct interpretation

This is not acceptable for v0.8.

## Primary Understanding Source-Of-Truth Rule

v0.8 must make the primary understanding artifact the source of truth for the user turn.

This means:

- one turn gets one `primary_understanding_id`
- downstream artifacts must reference that id
- later stages may refine or supersede understanding only through explicit typed artifacts
- downstream stages must not silently substitute a different understanding basis

Allowed mechanisms for semantic change:

- `UnderstandingRefinement`
- `UnderstandingSupersession`

Disallowed mechanisms:

- mutating the original understanding object in place without a traceable event
- reparsing the raw utterance and replacing the original meaning with no explicit arbitration
- allowing later model outputs to overwrite earlier valid understanding because they arrived later

Required tests:

- a stable-turn flow preserves one `primary_understanding_id`
- a replanning flow still references the same `primary_understanding_id`
- a refinement flow emits explicit refinement linkage rather than silent replacement
- a supersession flow is visible in structured traces and does not erase prior artifacts

## Candidate Generation And Selection Boundary

v0.8 must define a strict split between host-owned candidate generation and model-guided candidate selection.

### Candidate generation is host-owned

Deterministic runtime code must generate a bounded `CandidateSet` containing:

- registered route candidates
- registered strategy candidates
- surface metadata
- capability metadata
- safety-relevant metadata needed before execution

The model must not directly create executable candidates.

### Candidate selection is model-guided but bounded

The model may only:

- rank candidates
- choose a candidate
- decline all candidates
- request clarification
- recommend downgrade order among existing candidates

The model must not:

- emit arbitrary executable authority
- invent a new candidate outside the `CandidateSet`
- bypass candidate generation by returning free-form action prose

Required implementation rule:

- candidate selection outputs must identify existing candidate ids
- non-selection must be represented structurally
- the runtime must be able to prove which candidate set was shown to the model

Required tests:

- selection is constrained to candidate ids
- unknown candidate ids are rejected deterministically
- empty or inadequate candidate sets force structured non-selection rather than hidden fallback invention
- semantically equivalent phrasing still maps into a valid host-owned candidate family without target-specific patching

## Model Budget Discipline

v0.8 must increase model participation without becoming token-wasteful.

The system should use the following design discipline.

### 1. Full-context understanding once per turn

The initial task-understanding call may use the full user utterance and relevant compact context.

### 2. Structured downstream prompts

Later calls should consume structured artifacts such as:

- prior understanding
- candidate routes
- failure summaries
- observation summaries

rather than the raw full conversation whenever possible.

### 3. Model escalation by uncertainty

If a cheap model yields low confidence or structured uncertainty, the system may escalate to a stronger model.

It should not always pay the strongest-model cost by default if a cheaper model is sufficient.

### 4. No repeated hidden semantic retries

The runtime must not silently make multiple full semantic parses of the same request unless:

- the previous result was structurally invalid
- the previous result was explicitly marked uncertain
- new evidence materially changes the interpretation problem

### 5. Reuse evidence summaries

Observation packages and semantic summaries should be cached per run and reused across replanning and acceptance.

### 6. Spend tokens where rules are weak

Tokens should be spent on:

- understanding
- route / strategy choice
- replanning
- semantic evidence interpretation
- acceptance

Tokens should not be wasted on:

- capability registry lookup
- deterministic normalization
- schema validation
- approval record persistence

## Model Usage Accounting

v0.8 must make token-discipline and parse-reuse behavior inspectable through structured runtime data.

At minimum, structured runtime artifacts should expose fields equivalent to:

- `primary_understanding_call_count`
- `model_reparse_count`
- `full_context_call_count`
- `structured_followup_call_count`
- `artifact_reuse_count`
- `semantic_summary_cache_hit_count`
- `escalation_count`

Required rules:

- these counters must be derived from real runtime behavior, not guessed after the fact
- traces must make visible when a downstream call reused earlier artifacts
- repeated reparsing must carry an explicit reason when it happens

Required tests:

- one stable turn records one primary understanding call by default
- downstream route / replan / acceptance calls reuse artifacts without incrementing reparse count
- escalation increments explicit counters
- repeated parse attempts without a valid reason are detectable as test failures

## Required Logging And Trace Integration

v0.8 must integrate all new semantic artifacts with the existing host-owned logging chain.

This includes:

- `audit.jsonl`
- run-scoped trace artifacts
- `events.jsonl`
- `model_io.jsonl`
- typed `RunLedger`
- structured summaries and manifests

It is not acceptable to implement new semantic state only as ephemeral in-memory objects or only as debug-only prose.

### Audit requirements

Final audit records must expose enough information to correlate the run with its semantic artifacts.

At minimum, audit records for relevant turns should include fields equivalent to:

- `trace_run_id`
- `understanding_id`
- `candidate_set_id`
- `selected_route_decision_id`
- `selected_strategy_decision_id`
- `semantic_acceptance_decision_id`

The audit layer does not need to inline every artifact payload, but it must provide stable references.

### Trace-event requirements

Run-scoped trace events must record the creation and consumption of semantic artifacts.

At minimum, trace events should be able to show:

- artifact type
- artifact id
- source artifact ids
- whether the artifact was primary, refinement, or supersession
- whether candidate generation or selection occurred
- whether semantic summary reuse occurred

### Model IO requirements

Model IO logs must record which structured artifacts were provided to the model.

At minimum, model IO records should be able to show:

- which `understanding_id` was consumed
- which `candidate_set_id` was consumed
- which failure / observation / semantic-summary artifacts were consumed
- whether the call was a full-context understanding call or a structured follow-up call

### Run ledger requirements

Run-ledger attempt and strategy history must reference semantic artifacts, not only route ids.

At minimum, the ledger should be able to expose fields equivalent to:

- `understanding_id`
- `candidate_set_id`
- `route_decision_id`
- `strategy_decision_id`
- `semantic_summary_id`
- `step_safety_review_ids`

### Required logging tests

Codex must not treat v0.8 as complete without deterministic tests proving:

- one turn's semantic artifacts can be correlated across audit, trace, model IO, and ledger
- replanning preserves `understanding_id` continuity
- semantic acceptance decisions can be traced back to their evidence summary and hard facts
- repeated parsing and artifact reuse are visible in structured logs

## Required Deliverables

### 1. Model-led task-understanding layer

Add a typed understanding layer that:

- is model-led
- can represent uncertainty explicitly
- captures goal, target, ambiguity, and expected completion
- is serializable into structured traces

### 2. Model-guided route decision layer

Introduce a constrained decision layer where the model selects among host-owned route and strategy candidates.

### 3. Centralized step safety review

All executable steps must pass through one explicit host-owned safety review layer immediately before execution.

### 4. Model-guided replanning

Replanning must consume structured prior evidence and preserve goal continuity.

### 5. Semantic evidence summary layer

Add a structured semantic interpretation layer over observations and verifier results.

### 6. Rule + model acceptance engine

Acceptance must combine hard deterministic facts with model-guided semantic completion judgment.

### 7. Token-efficient orchestration

The runtime must show explicit evidence that it:

- reuses prior model artifacts
- avoids repeated parsing
- limits full-context calls
- uses escalation rather than brute-force repetition

## Minimal v0.8 Vertical Slices

v0.8 must prove the new architecture with deterministic local slices.

Required slices for v0.8 completion are exactly:

- Slice A: Named website opening
- Slice B: Ambiguous user request

App-local search is intentionally excluded from the required slice set for v0.8, even if a fixture already exists.

### Slice A: Named website opening

Recommended scenario:

```text
user goal: "帮我打开百度官网"

understanding:
  model identifies named website opening goal

planning:
  host-owned candidates exist
  model selects direct-open or search-follow-up first

safety:
  each executable browser step is reviewed before execution

acceptance:
  search page alone is not equal to official-site completion
  semantic acceptance uses observation evidence plus hard verifier facts
```

### Slice B: Ambiguous user request

Recommended scenario:

```text
user goal: "open that site we discussed yesterday"

understanding:
  model identifies insufficient target specificity

clarification:
  model generates the minimal missing-information question

execution:
  no executable step is run before clarification resolves the ambiguity
```

## Stretch Slice

The following slice may be implemented if lower-layer fixture support is already stable, but it is not required for v0.8 completion.

### Stretch Slice: App-local search interaction

This slice remains optional even if a local fixture is already stable.

It may be used as additional confidence-building coverage, but it must not become a hidden completion gate for v0.8.

Example:

```text
user goal: "search chat history in WeChat for Alice"

understanding:
  model identifies in-app search goal and completion semantics

planning:
  structured strategy and shortcut fallback are both available

replanning:
  model chooses fallback or clarification based on structured failure evidence

acceptance:
  semantic result judgment depends on observed results, not only route completion
```

This slice should not be used as a hidden prerequisite for declaring the semantic middle layer healthy.

## Required Test Matrix

Codex must not treat v0.8 as complete without deterministic tests covering all of the following classes.

### 1. Task-understanding tests

- model-led understanding artifact shape
- uncertainty representation
- no repeated semantic parse on a stable turn unless required

### 2. Route-decision tests

- registered candidates exposed to the decision layer
- model-guided selection remains constrained to allowed routes
- semantically equivalent phrasing still reaches the correct candidate family

### 3. Safety-boundary tests

- no lexical pre-rejection for dangerous-looking words alone
- every executable step emits a centralized safety review
- denied or review-required steps do not execute

### 4. Replanning tests

- replanning consumes prior structured evidence
- goal identity remains stable
- strategy replacement is model-guided but bounded

### 5. Semantic acceptance tests

- route success but semantic non-completion
- hard verifier failure overrides model optimism
- semantic evidence can turn a mechanically incomplete route into an explicit incomplete outcome rather than false success

### 6. Token-discipline tests

- one primary understanding artifact per user turn
- downstream stages reuse prior artifacts
- no hidden multi-parse loops on the same utterance without a traceable reason

### 7. Trace and audit tests

Structured runtime outputs must expose enough information to prove:

- primary task understanding artifact
- route / strategy decision inputs and outputs
- per-step safety review
- replan decisions
- semantic acceptance basis
- token-reuse / parse-reuse evidence where applicable

## First Failing Tests

Codex should establish an early failing test set before large-scale implementation work.

At minimum, this set should include deterministic tests for:

- one primary understanding artifact per stable user turn
- silent reparse or silent understanding replacement is rejected
- unknown or out-of-set `candidate_id` is rejected deterministically
- `safety deny` overrides optimistic model judgment
- search result page does not count as official-site completion
- insufficient evidence cannot be upgraded to `completed`

These tests should fail before the v0.8 implementation is complete and pass only when the core architectural guarantees are real.

## Required Result Semantics

For v0.8 work, Codex must preserve structured result semantics.

This means:

- `overall_status` remains the first-order final judgment
- `execution_status` remains necessary but insufficient
- `acceptance_status` must remain distinct from execution state
- model-guided semantic conclusions must be visible through structured fields, not only prose

## Migration Discipline

Codex should implement v0.8 in a staged way.

Recommended order:

1. introduce the primary model-led understanding artifact
2. remove lexical safety blocking from understanding
3. centralize per-step safety review
4. convert route selection into constrained model-guided decision-making
5. upgrade replanning to consume structured evidence with model guidance
6. add semantic evidence summary
7. upgrade acceptance to rule + model completion judgment
8. tighten token-discipline and trace reuse guarantees

If implementation must stop mid-way, partial states should still preserve current v0.7 correctness and must not silently expand authority.

## Codex / WSL Acceptance Boundary

v0.8 acceptance must remain inside work Codex can complete in the repository or in WSL.

Codex-owned acceptance may include:

- deterministic local fixtures
- unit and integration tests
- planner / broker / runtime JSON contract checks
- `pytest -q`
- explicit fake-model or fixture-provider tests
- trace and audit contract checks
- WSL-safe checks as described in `docs/zh_cn/07_wsl_test_standard.md`

Codex-owned acceptance must not require:

- a real public-site network load
- a real WeChat installation
- a real Linux accessibility bus
- real OCR as a mandatory dependency
- real uncontrolled desktop automation

## Offline Model Acceptance Rule

Local v0.8 acceptance must not depend on:

- a real remote LLM succeeding
- a real remote LLM failing and then falling back
- environment-variable-dependent model availability
- live network behavior

Instead, local acceptance must explicitly inject deterministic fake model providers or fixture providers.

Required rule:

- if a test is supposed to exercise model-led understanding, route decision, replanning, semantic summary, or acceptance, it must do so through an explicit fake or deterministic test provider

Disallowed local-acceptance pattern:

- "the real provider happened to be unavailable, so the test passed through fallback"

This is not stable enough for Codex-owned acceptance.

## Disallowed Shortcuts

The following are not acceptable v0.8 solutions:

- adding more deterministic keyword routing to simulate semantic understanding
- keeping route planning rule-led and only renaming it as model-guided
- using lexical front-door safety rejection instead of step-boundary safety review
- repeatedly reparsing the same utterance until one model output looks convenient
- letting a later malformed parse overwrite an earlier valid understanding without explicit arbitration
- broadening model authority so that unregistered capabilities or hidden tools become possible
- claiming token efficiency by removing model participation from semantically critical stages
- claiming semantic acceptance while still only checking route completion

## Success Criteria

v0.8 is healthy when the repository can demonstrate all of the following locally:

- natural-language task understanding is model-led
- route and strategy choice are model-guided inside host-owned boundaries
- lexical danger words do not cause front-door rejection by themselves
- every executable step is reviewed by a centralized safety layer before execution
- replanning is model-guided from structured evidence rather than only rule-scripted
- semantic evidence summary exists as a first-class runtime artifact
- acceptance combines hard verifier facts with semantic completion judgment
- repeated full semantic parsing of the same user turn is no longer the default behavior
- token discipline is visible in traces or structured runtime artifacts
- no required v0.8 test depends on live network, real WeChat, or uncontrolled real desktop execution

## Final Design Summary

v0.8 should move VibeOS from:

- a typed personal-agent runtime that still relies too heavily on deterministic semantic rules

to:

- a model-centered personal-agent runtime in which understanding, planning, replanning, and semantic completion are model-guided, while capability exposure, safety review, normalization, execution, and audit remain host-owned

The system should become more semantically capable without becoming less inspectable, less governable, or less efficient.
