# VibeOS v0.5 Goal For Codex

Last updated: 2026-06-04

## Purpose

This document is the implementation brief for **VibeOS v0.5: goal synthesis, acceptance verification, and model-visible debug architecture**.

It is intentionally limited to work Codex can implement and verify inside the local repository. Fedora VM integration and real desktop validation remain out of scope for v0.5 acceptance and will be handled later by the user.

v0.5 should be treated as the next architectural step after v0.4. It should not be a loose feature expansion. It should tighten the agent into a shape that is more consistent with mature coding agents, tool-using assistants, and automotive voice-assistant systems:

- stable capability and domain boundaries
- open-ended goal handling above those boundaries
- explicit completion verification after execution
- structured traceability for debugging model and planner behavior

## Goal Prompt

You are working on the `vibeos` repository.

Your goal is to implement VibeOS v0.5 on top of the existing v0.4 typed task pipeline.

Do not replace the typed `TaskPlan`, validation, review, execution graph, verification, audit, or daemon transport layers.

Do remove the old direct legacy execution path from the primary agent flow for supported tasks.

The problem to solve is not "add more random domains". The problem is that the current agent still has three major architectural gaps:

- it can route into domains, but it cannot robustly synthesize open-ended user goals from the capabilities it is actually allowed to use
- it can execute actions, but it cannot reliably decide whether the user goal was actually completed
- it exposes some structured trace, but it still does not expose enough model and planner decision data for serious debugging

v0.5 must add a **goal synthesis layer** parallel to the domain layer, a **post-execution acceptance subsystem**, and a **debug trace layer** that makes model outputs and planning decisions inspectable.

The v0.5 design target is:

```text
utterance
  -> utterance analysis
  -> goal synthesis
  -> domain routing
  -> observation request
  -> context package resolver
  -> capability exposure manifest
  -> candidate plans from active domains only
  -> route and plan selection
  -> validation
  -> review
  -> execution
  -> post-execution observation
  -> acceptance engine
  -> run trace, debug trace, and audit
```

For supported executable tasks, the primary path must no longer be:

```text
utterance -> legacy single Intent -> direct adapter execute
```

That path may remain only as an internal compatibility helper during migration if absolutely necessary, but it must not remain the normal `vibe ask` / `vibe plan` path for supported tasks.

## Proven Patterns To Follow

v0.5 should follow mature agent design patterns:

- Codex-style tool agents keep tool boundaries code-enforced, surface structured intermediate artifacts, and make execution traceable.
- Claude Code-style workflows separate planning, permission, execution, and results instead of hiding everything behind one model call.
- Hermes-style systems use stable tool and capability boundaries, explicit context scoping, and planner-visible tool metadata rather than global prompts.
- Automotive voice assistants and smart cockpit systems route into bounded skill domains, then perform slot filling, action planning, and completion checks before reporting success.

For VibeOS, the equivalent is:

- domains remain stable, host-owned, and versioned
- goals may be open-ended, but must be composed only from allowed capabilities
- execution success is not the same thing as user-goal completion
- traces must show what the model proposed, what the planner accepted, and why the final outcome was considered complete or incomplete

These patterns are guidance, not product claims. v0.5 must stay model-provider agnostic and must not depend on live network access, remote LLM success, VM state, or a real desktop session for local acceptance.

Important offline boundary: local acceptance must explicitly use `RuleIntentBroker`, fake brokers, or fake synthesis providers. It is not enough to rely on a remote broker failing and falling back locally. A machine with `OPENAI_API_KEY`, `DEEPSEEK_API_KEY`, `OPENAI_MODEL`, or similar variables must still run the same deterministic local acceptance path.

## Architectural Decisions

### 1. Static domains remain host-owned

Do not implement runtime domain creation or dynamic domain registration by the model.

The model may propose:

- a goal decomposition
- composition hints for planning
- a missing capability report
- a domain or route proposal for future implementation

But the model must not modify the live `DomainRegistry`.

`DomainRegistry` remains a stable platform boundary, not a model-generated scratchpad.

### 2. Add goal synthesis parallel to domains

Do not create a catch-all "misc" or "unknown" domain that acts like the old `intent.py`.

Instead, add a separate **goal synthesis layer** that:

- interprets open-ended user requests
- decomposes them into subgoals
- maps those subgoals onto existing domains and capability families
- returns clarification or missing-capability reports when the platform cannot satisfy the request

This layer may be model-assisted, but it must output typed structures rather than free-form reasoning.

Important boundary:

- goal synthesis is not the planner
- goal synthesis must not emit final `TaskPlan` or final executable task graphs
- goal synthesis may emit constraints, candidate domains, fallback hints, and missing-capability reports
- the actual `TaskPlan` must still be generated by the planner from registered domains and routes

### 3. Add a real acceptance subsystem

Do not treat adapter success as user-goal success.

Add a platform-level **acceptance engine** that consumes:

- the selected plan
- execution results
- post-execution observation packages
- domain-owned verifier specs

and returns a separate acceptance result.

The framework must be platform-owned. Domain-specific acceptance rules must be domain-registered.

Important boundary:

- v0.5 should not create a second independent verifier stack next to v0.4 verifiers
- `VerifierRegistry` remains the rule-level checking mechanism
- the acceptance engine aggregates execution results, post-execution observation, and verifier outputs into a user-goal completion judgment

### 4. Expose model and planner decisions through debug trace

Do not require hidden chain-of-thought.

Do expose:

- normalized model outputs by default, with optional raw payload visibility only in debug mode
- parsed goal synthesis artifacts
- route competition
- fallback reasons
- review, execution, and acceptance evidence

Use structured debug objects, not unbounded prose reasoning.

## v0.5 Scope Decision

v0.5 should improve real agent behavior, but stay bounded enough for Codex to finish locally.

### In scope

- goal synthesis layer
- removal of primary-path legacy single-intent execution for supported tasks
- explicit stable domains for current executable capability families
- acceptance engine with browser-focused failure semantics
- debug trace including model exchange visibility
- deterministic local tests and fixtures

### Out of scope

- runtime model-created domain registration
- arbitrary plugin or MCP execution as a v0.5 dependency
- real browser DOM scraping, browser automation, or screenshot OCR as a local acceptance requirement
- real network-dependent checks such as loading Google successfully
- VM-only verification as a completion gate

## Required Deliverables

Implement the following local architecture pieces.

### 1. Goal synthesis layer

Add a typed goal-synthesis module parallel to the domain router.

It should convert a user request into a structured goal object before route selection.

Required responsibilities:

- identify the primary user goal
- identify subgoals
- identify required capability families
- identify candidate domains
- identify missing slots or missing capabilities
- produce planner-facing synthesis constraints using only registered capabilities and domain metadata
- explicitly mark fallbacks and assumptions

Required output shape should include fields equivalent to:

- `goal_id`
- `goal_text`
- `goal_type`
- `subgoals`
- `candidate_domain_ids`
- `required_capability_ids`
- `missing_capability_ids`
- `clarification_questions`
- `constraints`
- `fallback_hints`
- `synthesis_provenance`

This layer may call a model-facing provider, but only through a narrow structured interface. It must not emit free-form shell commands, raw D-Bus method names, or arbitrary code.

The planner remains responsible for:

- choosing actual routes
- constructing the final `TaskPlan`
- route competition and scoring
- producing validation-ready step graphs

### 2. Stable explicit domains for legacy capability families

v0.4 made `browser` and `media` explicit. v0.5 must do the same for currently supported non-browser capability families.

Required new domain packs:

- `apps`
- `window_management`
- `clipboard`
- `notification`
- `system_observation`

`browser` and `media` remain.

Special migration notes:

- `portal.open_uri` may remain as a low-level primitive used by browser-domain execution, but it must not remain a primary planner-selected route for supported browser tasks
- `media.search`, `media.play`, and `media.pause` may remain partially unavailable on the local host, but their planning and fallback behavior must still be explicit and non-legacy

Each must define:

- routes
- allowed context package IDs
- capability families
- default verifier IDs
- policy defaults

For supported tasks, successful executable plans should now come from explicit domains plus planner-generated task plans, not `legacy_*_route` normalization.

v0.5 should migrate current supported legacy capability families into explicit domains. It should not simultaneously expand those domains with new capability families beyond the current repository surface.

### 3. Remove legacy direct-intent execution from the supported-task main path

Refactor the primary agent flow so that supported executable tasks do not rely on the old direct `intent_broker.parse(...) -> Intent -> _execute(...)` path.

Important boundary:

- this does not mean deleting `_execute()` or removing adapter dispatch
- `_execute()` may remain as the step-level adapter dispatch layer for validated `TaskPlan` steps
- what must be removed from the supported-task main path is:

```text
utterance -> single Intent -> policy -> _execute
```

Required outcome:

- `vibe plan` and `vibe ask` for supported tasks must produce v0.5 domain or synthesized plans
- successful executable plans must not use `legacy_intent_bridge` provenance
- successful executable plans must not expose `legacy_*_route` as the selected route
- when a supported domain plan cannot be formed, the system must return a structured planner or domain error rather than silently falling back to `legacy_*_route`

If a compatibility helper remains during migration, it must be isolated and clearly marked as non-primary. It must not silently become the planner for normal supported tasks.

### 4. Acceptance engine

Add a typed acceptance subsystem that is clearly separated from raw adapter execution.

Required concepts:

- post-execution observation request
- post-execution observation receipt
- acceptance status
- acceptance evidence
- acceptance failure reasons

Suggested acceptance states:

- `passed`
- `failed`
- `indeterminate`
- `skipped`

Required behavior:

- a command may execute successfully but fail acceptance
- top-level command outcome must reflect that difference
- the user-facing payload must not present a failed acceptance as full task completion

The acceptance engine should aggregate:

- execution status
- post-execution observation packages
- verifier outputs from the existing verifier system
- domain-level completion expectations

For example:

- browser launch succeeds but browser shows a TLS error page
- browser launch succeeds but observation indicates HTTP 404
- browser launch succeeds but no expected query or URL can be observed

These must not be treated as clean completion.

### 5. Browser-focused acceptance semantics

v0.5 acceptance must prove the architecture with browser outcomes.

Required browser acceptance signals for local fixtures and tests:

- URL observed as expected
- query observed as expected
- explicit browser error state such as `tls_error`, `dns_error`, `network_error`, or `http_404`

Local acceptance may use fake browser observation fixtures. It must not require a live browser session or network connectivity.

### 6. Debug trace and model-exchange visibility

Add a separate debug trace layer.

`run trace` should remain the general per-turn lifecycle trace.

`debug trace` should expose additional structured debugging data, especially for model-assisted stages.

Required debug-trace sections:

- utterance analysis inputs and outputs
- goal synthesis input, normalized output, and provenance
- model exchange metadata
- synthesis constraints and fallback hints
- candidate route competition
- fallback and elimination reasons
- review decision
- execution results
- acceptance results

Model exchange visibility must support:

- provider name
- model name
- normalized response payload by default
- optional raw response payload only in debug mode
- parse/validation result
- fallback-used flag
- error details when parsing fails

Secrets must be redacted. Hidden chain-of-thought is not required and must not be the debugging contract.

Raw prompt/response visibility requirements:

- raw model payload must be gated behind an explicit debug flag
- raw model payload must be redacted
- raw model payload must be size-limited
- raw model payload must not be written into audit logs by default

### 7. Explicit model-facing provider boundary

The current repository already has broker code in `intent.py`. v0.5 must introduce a cleaner structured provider boundary for model-assisted synthesis and analysis.

This provider boundary should:

- accept typed input
- request structured JSON output
- validate output before it enters planning
- expose normalized provider output by default and raw provider output only in debug mode
- allow deterministic fake providers in tests

The provider boundary must not let raw model text directly drive adapter execution.

### 8. Clarification and missing-capability reporting

When the system cannot solve an open-ended request with the available capabilities, it must not collapse into a generic domain miss.

Instead, it should return structured outcomes such as:

- clarification needed
- missing capability
- unsupported due to policy
- unsupported due to unavailable observation or verifier support

The output must show what the system understood and what specifically blocked execution.

### 9. Top-level status semantics

Revise top-level result semantics so the public outcome reflects the difference between:

- planning success
- execution success
- acceptance success

v0.5 should not report a task as cleanly completed if:

- execution succeeded but acceptance failed
- execution succeeded but acceptance is indeterminate and the task requires confirmation of real completion

You may keep backward-compatible fields if needed, but the new semantics must be unambiguous in JSON output.

Required public status fields:

- `execution_status`
- `acceptance_status`
- `overall_status`

The mapping between them must be explicit and testable. A plain top-level `status: executed` is not sufficient as the only public outcome signal.

This requirement applies to:

- direct `vibe ask`
- `vibe approve <review_id>`
- daemon approval responses over D-Bus and HTTP

Required mapping table:

| Situation | execution_status | acceptance_status | overall_status |
| --- | --- | --- | --- |
| planning failed before execution | `not_started` | `skipped` | `failed` |
| review required before execution | `not_started` | `skipped` | `needs_review` |
| dry run completed | `dry_run` | `skipped` or `indeterminate` | `dry_run` |
| execution failed before postcondition checks | `failed` | `skipped` | `failed` |
| execution succeeded and acceptance passed | `succeeded` | `passed` | `completed` |
| execution succeeded and acceptance failed | `succeeded` | `failed` | `incomplete` |
| execution succeeded and acceptance indeterminate | `succeeded` | `indeterminate` | `incomplete` |

Exact enum names may differ if the schema is coherent, but the distinction above must be preserved and covered by tests.

Recommended rule:

- use `failed` only when execution itself failed or the plan could not be executed
- use `incomplete` when execution happened but user-goal completion was not accepted

### 10. Run trace remains structured and audit-friendly

Retain and extend the v0.4 trace model.

Required trace coverage:

- utterance analysis
- goal synthesis
- domain routing
- observation request and receipt
- capability exposure
- candidate plan selection
- validation
- review
- execution
- acceptance
- debug-trace linkage

Audit entries must remain append-only and must capture enough information to reconstruct why the system claimed success, failure, or incompleteness.

Debug trace and audit boundary:

- raw model payload belongs in debug trace only by default
- normalized structured outputs may appear in audit when useful
- audit must not store raw model prompt or raw model response by default
- if raw model payload is ever written to audit under an explicit debug mode, that path must be separately redacted and size-limited

## Required Behavioral Changes

The repository should satisfy all of the following local behaviors by the end of v0.5.

### A. Open-ended goal synthesis

The system should handle higher-level goals by composing allowed capabilities rather than only matching one domain phrase.

Examples of acceptable local-test behavior:

- a multi-step or open-ended request can produce a typed `GoalSpec` with subgoals, candidate domains, and constraints
- an open-ended request that cannot be completed returns a structured missing-capability result instead of a generic unknown-domain failure

### B. No primary-path legacy route for supported tasks

Supported tasks should not rely on `legacy_*_route` in their normal path.

### C. Acceptance distinguishes launch from completion

Browser open or search should not be considered complete merely because `xdg-desktop-portal` or `xdg-open` returned success.

### D. Debug trace exposes model and planner artifacts

Codex and the user must be able to inspect what structured output the model provider returned, what was parsed, what was rejected, and why a plan was selected.

### E. Deterministic local tests

All acceptance must be provable with fake providers, fake observations, and local fixtures.

## Local Acceptance Criteria

v0.5 counts as complete only if all of the following are true in the local repository.

### 1. Full automated test pass

`pytest -q` passes locally in the intended development environment.

### 2. Goal synthesis has typed local coverage

Local tests prove:

- open-ended requests produce a typed goal-synthesis artifact
- supported requests produce planner-facing `GoalSpec` artifacts using registered capabilities and domain hints
- unsupported requests return structured clarification or missing-capability output
- fake providers can drive synthesis deterministically

### 3. Supported tasks avoid legacy route selection

Local tests prove that supported executable tasks do not return:

- `legacy_intent_bridge` provenance
- `legacy_*_route` selected routes

for their primary successful path.

### 4. Acceptance failures propagate correctly

Local tests prove:

- execution success plus acceptance failure does not present as clean completion
- execution success plus indeterminate acceptance is distinguishable from full success
- browser fixture cases such as `tls_error`, `dns_error`, `network_error`, or `http_404` produce failed or incomplete acceptance

### 5. Browser success and failure fixtures are both covered

Local tests prove:

- observed URL success
- observed query success
- browser error-page or failure observations

using fake or local harnesses only.

### 6. Debug trace exposes structured model output

Local tests prove debug mode includes structured visibility for:

- provider metadata
- normalized model output by default
- raw model output only when the debug flag is enabled
- parse validation outcome
- fallback use
- selected route
- acceptance outcome

### 7. Offline deterministic path remains stable

Local tests prove:

- `RuleIntentBroker` or fake providers can run end-to-end without network
- local acceptance does not depend on remote provider failure
- debug trace still works in deterministic local mode

### 8. Public JSON remains usable

`vibe plan --json` and `vibe ask --json` remain machine-readable and expose enough metadata to identify which layer failed:

- analysis
- goal synthesis
- domain routing
- observation
- capability exposure
- validation
- review
- execution
- acceptance
- trace

### 9. Audit and review remain coherent

Local tests prove:

- review storage still works for L2 actions and plan-based reviews
- audit entries can distinguish execution success from acceptance outcome

## Local Completion Examples

The following should be locally testable with deterministic providers and harnesses.

### Example 1: browser search plan

`vibe plan "search web for hello" --json --offline`

Expected:

- v0.5 schema or trace metadata
- goal synthesis artifact
- browser domain selected
- browser search route selected
- no legacy selected route

### Example 2: browser search dry run

`vibe ask "search web for hello" --json --offline --dry-run`

Expected:

- synthesized plan
- review result
- no real adapter execution
- acceptance trace present but marked skipped or indeterminate

### Example 3: browser search execution with failing acceptance fixture

Using a fake observation fixture equivalent to a TLS or network error:

- execution succeeds in opening the browser target
- acceptance fails
- top-level outcome does not present as clean completion

### Example 4: open-ended unsupported request

A request outside the currently registered capability families should return:

- structured goal synthesis output
- explicit missing capability or clarification data
- no generic domain miss as the only explanation

## Implementation Order

Codex should implement v0.5 in this order:

1. evacuate legacy supported capabilities into explicit stable domains without widening capability scope
2. add typed goal-synthesis models and provider boundary; synthesis outputs `GoalSpec` rather than final `TaskPlan`
3. remove legacy direct-intent execution from the supported-task main path
4. add browser-focused acceptance by aggregating post-execution observation with existing verifier outputs
5. add debug trace and model-exchange visibility with redaction, size limits, and explicit debug gating
6. propagate new status semantics through broker, CLI, daemon payloads, audit, and tests
7. update or add documentation summarizing what was implemented

Do not start by widening the model prompt or adding random new capabilities. The architecture must be tightened before expanding scope.

## Non-Goals

The following are explicitly not required for v0.5 completion:

- real VM-side proof of browser success or browser failure pages
- real DOM scraping or browser automation
- real playback automation for media
- runtime domain generation by the model
- general shell-command execution
- arbitrary file operations outside the current capability scope

## Final Standard

Do not count v0.5 as complete if only trace output changed.

Do not count v0.5 as complete if goal synthesis still collapses into the old direct single-intent path for supported tasks.

Do not count v0.5 as complete if acceptance failure is still surfaced as clean task success.

Do not count v0.5 as complete if model outputs remain opaque during debugging.

v0.5 is complete when the local codebase proves all of the following:

- domains remain stable and host-owned
- open-ended goals are synthesized from allowed capabilities rather than generic fallback intent parsing
- supported tasks plan through explicit domains and typed task plans
- execution is separate from acceptance
- acceptance can fail even when adapter launch succeeded
- model and planner decisions are visible through structured debug trace
- all of this is locally testable without VM dependence
